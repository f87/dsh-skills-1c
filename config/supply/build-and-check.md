# Сборка `.bin` с несколькими поставками, загрузка и приёмка

Универсально: `<tree>` — дерево конфигурации в файлах, `<ib>` — файловая база, `<cf>` — файл
конфигурации, `$exe` — путь к `1cv8.exe` ([`../../1cv8/environment.md`](../../1cv8/environment.md)).
Проверено 8.3.27.1859, 28.10.2026.

Правила и признаки — [`deliveries.md`](deliveries.md), [`which-is-main.md`](which-is-main.md).

---

## 0. Состав на входе (до сборки)

Состав берётся из исходной конфигурации, а не из задания: число поставок в рабочей базе или эталоне и
число копий `*.cf` в `Ext\ParentConfigurations\`. Если в задании написано «собрать с одной поставкой»,
а в исходнике их две — задание устарело
([`../update/traps.md`](../update/traps.md) п.17), собирать по нему нельзя: дерево с одной поставкой
молча выключает дополнение из поддержки.

```powershell
node config\supply\bin_summary.js <sourceTree>\Ext\ParentConfigurations.bin   # эталон «как было»
node config\supply\bin_summary.js <tree>\Ext\ParentConfigurations.bin         # то, что собираемся грузить
```

`count` и пары `name`+`version` должны совпасть (R20); дальше —
[`../update/deliveries-invariance.md`](../update/deliveries-invariance.md).

## 1. Посмотреть, что есть сейчас

```powershell
node config\supply\bin_summary.js <tree>\Ext\ParentConfigurations.bin
```

Смотреть: `flag`, `count`, `supportGuid`, `ownDelivery` (какая поставка «своя»: `parentGuid ==
supportGuid`), по каждой поставке — `name`/`version`/`vendor`, `parentGuid`, `flag`, число записей и
распределение уровней. Сравнить два файла: `node config\supply\bin_diff.js <a.bin> <b.bin>` (коды
`0` — идентично, `1` — отличия, `2` — ошибка чтения).

## 2. Определить порядок

Главная поставка — первая: совпадение `name`+`version` с `Configuration.xml` цели, иначе вендор
продукта ([`which-is-main.md`](which-is-main.md)).

## 3. Собрать `.bin` из двух одноставочных

Вход — по одному файлу `.bin` на поставку (например, из выгрузок вендорских `.cf`: у одноставочной
выгрузки `count=1`, `parentGuid == supportGuid`).

```powershell
node config\supply\build_two_deliveries_bin.js `
  --main  <bin главной поставки> `
  --extra <bin дополнительной поставки> `
  --mode vendor --order main --header main `
  --flag 0 --flag-main 0 --flag-extra 0 `
  --out <new.bin> --write
```

| Ключ | Смысл |
|---|---|
| `--mode vendor` | записи переносятся как в вендорском файле (уровни вендорские) |
| `--mode adapt` | уровни переносятся по UUID из эталона `--ref`; лишнее фильтруется по `--cdi` (нет в `ConfigDumpInfo` / уже занято главной) |
| `--order main\|extra` | порядок поставок в файле; `main` = главная первой (конвенция) |
| `--header main\|extra\|<guid>` | заголовочный `supportGuid`; `main` = guid главной поставки |
| `--flag`, `--flag-main`, `--flag-extra` | флаги: `0` — копия `*.cf` остаётся, `1` — 1С её удалит |
| `--parent-main`, `--parent-extra` | задать `parentGuid` поставки явно |
| `--tail auto\|ref` | хвост по умолчанию или из эталона `--ref` |
| `--config <Configuration.xml>` | сверить `name`+`version` главной поставки с целью (расхождение — warning, с `--strict` — ошибка) |
| `--ref` | эталонный `.bin` для `--mode adapt` / `--tail ref` |
| `--cdi` | `ConfigDumpInfo.xml` для фильтра записей в `adapt` |
| `--allow-dupes` | не считать ошибкой пересечение UUID между поставками |

Без `--write` — только отчёт (dry-run). Сборщик проверяет: `count=2`, round-trip токенов,
`N` = число записей, имена/версии поставок, `parentGuid` первой = `supportGuid`, пересечения UUID.
Любая проверка не прошла — файл не пишется (коды `0/2/3/4/5`). Отчёт — JSON: размеры, SHA1, токены,
уровни по поставкам, warnings (в том числе «флаг 1 → 1С удалит копию `.cf`»).

## 4. Подготовить дерево

```powershell
robocopy <tree> <tree2> /E /COPY:DAT /DCOPY:T /R:1 /W:1 /MT:16
Copy-Item <копия дополнения>.cf <tree2>\Ext\ParentConfigurations\<Имя поставки>.cf
Copy-Item <new.bin> <tree2>\Ext\ParentConfigurations.bin -Force
(Get-FileHash <tree2>\Ext\ParentConfigurations.bin -Algorithm SHA1).Hash   # сверить с отчётом сборщика
```

Имя копии = поле `name` поставки в `.bin`. Копия — **байтовая** копия вендорского `.cf` (сверить SHA1).

## 5. Загрузить и проверить синтаксис

```powershell
pwsh -File config\supply\load_tree.ps1 -Tree <tree2> -Ib <ib>\ib_load -LogDir <logs> -Tag load1 -CheckModules
```

Скрипт: чистая база (`-Force` — удалить существующую), `LoadConfigFromFiles`, подсчёт классов сообщений,
по `-CheckModules` — `CheckModules -ThinClient -Server`, по `-DumpFiles` — `DumpConfigToFiles` + SHA1
`.bin` после цикла + структура + копии, по `-CfOut` — `DumpCfg`. Сводка — `<logs>\<tag>.summary.json`.

**Ожидаемо:** `load: exit 0`, «Ошибка» = 0, «не соответствует» = 0; «Неизвестный объект» — столько,
сколько висячих ссылок в правах/планах (свойство дерева, не `.bin`); `checkmodules: exit 0`.
`-DumpFiles`: `binAfterCycle` = SHA1 собранного файла, копии — обе.

## 6. Выгрузить `.cf` и принять

```powershell
# .cf из уже загруженной базы
pwsh -File config\supply\load_tree.ps1 -Tree <tree2> -Ib <ib>\ib_load -LogDir <logs> -Tag load1 -CfOut <out.cf>

# приёмка «полным циклом»
pwsh -File config\supply\accept_cf.ps1 -Cf <out.cf> -Ib <ib>\ib_cf -LogDir <logs> -Tag cf1 `
  -Baseline <эталонное дерево> -ExpectedBin <new.bin> -Force
```

`accept_cf.ps1` в чистой базе: `LoadCfg` → классы сообщений → `CheckModules` → `DumpConfigToFiles` →
структура `.bin` (`bin_summary.js`) → копии `*.cf` с SHA1 → сверка дерева с эталоном через
`config\hash.js` с явным списком допустимых отличий. Отчёт — `<logs>\<tag>.acceptance.json`.
Коды: `0` — приёмка пройдена, `10` — база не создалась, `11` — `LoadCfg`, `12` — `CheckModules`,
`13` — выгрузка, `20` — шаги прошли, а сверка не сошлась. У `load_tree.ps1` те же `10–13` плюс
`14` — `DumpCfg`.

### Эталон для сверки

**Эталон — выгрузка, сделанная 1С** (из `.cf` или после цикла «загрузка → выгрузка»). Если эталон —
вендорская или вручную собранная выгрузка, которая через 1С не проходила, цикл даст несколько
**нормализаций**: 1С дописывает свойства по умолчанию, убирает `<Group>` с нулевым GUID из командных
интерфейсов, очищает `<Code>` у предопределённых элементов. Это не потеря данных, но каждое отличие
смотрите глазами и подтверждайте маской:

```powershell
pwsh -File config\supply\accept_cf.ps1 -Cf <cf> -Ib <ib>\ib_cf -LogDir <logs> -Tag cf1 `
  -Baseline <эталонное дерево> -ExpectedBin <new.bin> -Force `
  -Allow 'Catalogs/*/Ext/Predefined.xml','ExchangePlans/*.xml','Ext/MainSectionCommandInterface.xml'
```

Без `-Allow` такие файлы попадают в «изменено неожиданно» и приёмка не проходит (так и должно быть:
подтверждение — осознанное действие).

## 7. Критерии приёмки

| Проверка | Ожидание |
|---|---|
| сообщения `LoadCfg` | **0 любого класса** (лог — одна строка «Загрузка конфигурации успешно завершена») |
| `CheckModules -ThinClient -Server` | exit 0, «Синтаксических ошибок не обнаружено!» |
| `.bin` после цикла | SHA1 равен загруженному (1С структуру не переписывает) |
| копии `*.cf` | по одной на каждую поставку с `flag=0`, SHA1 = вендорским файлам |
| сверка с эталоном | потеряно 0 файлов; изменены только `Ext\ParentConfigurations.bin` и `ConfigDumpInfo.xml`; добавлена только копия `.cf` дополнения |
| нормализации 1С (если эталон не проходил через 1С) | подтверждены `-Allow` после просмотра: только дописанные свойства по умолчанию, удалённые `<Group>` с нулевым GUID, очищенные `<Code>` |

Код возврата `LoadCfg` сам по себе — **не** приёмка: он не показывает ни потерянных копий, ни
переписанной структуры.

## 8. Типовые отказы

| Симптом | Причина | Что делать |
|---|---|---|
| «Каталог не обнаружен `…\<Имя>.cf`» | у поставки `flag=0`, копии нет | положить байтовую копию `.cf` |
| копия дополнения исчезла после загрузки | у неё `flag=1` | пересобрать с `--flag-extra 0` |
| «196 “Тип предопределённого вида характеристики…”» | висячие ссылки на удалённые объекты, а не поставки | чистить ссылки (`config/update/prunerefs.js`) |
| `N` не совпадает с числом записей | битый `.bin` (потерян токен) | пересобрать: сборщик проверяет `N` |
| `.bin` после цикла отличается по SHA1 | 1С пересчитала структуру (не наблюдалось) либо загружен другой файл | сверить, что в дереве лежит именно собранный `.bin` |
| сверка с эталоном показывает лишние отличия | сравнивается не тот эталон (другая версия/поставки) | эталон — выгрузка той же конфигурации той же версии |
| `CheckModules` = `101` на поставке-модуле | модуль ссылается на общие модули продукта (`УправлениеДоступом` и т. п.), а продукта в базе нет | это норма для одиночного модуля; проверять синтаксис только в сборке «продукт + модуль», для самого модуля — `-SkipCheckModules` |
| `CheckModules` = `1` | не запустился (лицензия, путь, занятая база) | смотреть `/Out`-лог, а не сообщения модулей |

## 9. Проверено на этих инструментах (28.10.2026, 8.3.27.1859)

Проверка — на одноставочной конфигурации (поставка-модуль 2.5.21.1, дерево 10 862 объекта) и на
пересборке двухпоставочного `.bin`:

| Что | Результат |
|---|---|
| `build_two_deliveries_bin.js`: пересборка двухпоставочного `.bin` из двух одноставочных при **том же** источнике уровней | SHA1 `17DE5CF2…` — **байт-в-байт** совпал с эталонным файлом (683 308 токенов, 170 816 записей) |
| то же при **другом** источнике уровней главной поставки (вендорский экспорт вместо собранного дерева) | те же размеры и состав, отличие только в уровнях главной поставки (159 943 записи `1` вместо `0`); ловится `bin_diff.js` |
| `bin_diff.js` на двух идентичных файлах | «структурно идентично», код `0`; на файлах с разным `flag` у второй поставки — «отличий 1», код `1` |
| `build_two_deliveries_bin.js --mode adapt` (dry-run, `--ref` + `--cdi` + `--config`) | сверка с целью прошла (`nameOk`/`versionOk`/`vendorOk`), фильтр отбросил записи, которых нет в `ConfigDumpInfo`, и записи, уже занятые главной; без `--cdi` пересечения UUID не отфильтрованы и сборка останавливается с подсказкой (`--cdi` либо `--allow-dupes`) |
| `load_tree.ps1` | `create` 2 с, `load` 72 с exit 0, 25 сообщений — все «Возможно неверная ссылка … внутри справки», `dumpfiles` 21 с (7 652 файла), `dumpcfg` 3 с; `.bin` после цикла **байт-в-байт** равен загруженному (`B81AF2D9…`) |
| `load_tree.ps1` на непустой базе без `-Force` | отказ с сообщением «база уже существует и не пуста» (защита от загрузки поверх) |
| `accept_cf.ps1` | `LoadCfg` 5–6 с, в логе одна строка «Загрузка конфигурации успешно завершена», 0 сообщений любого класса; выгрузка 16 с, 7 652 файла; `.bin` совпал с `-ExpectedBin`; сверка с эталоном: потеряно 0, неожиданно 0 (после `-Allow` на 5 нормализаций) → «ПРИЁМКА ПРОЙДЕНА», код `0` |
| `accept_cf.ps1` без `-Allow` | те же 5 файлов попали в «изменено неожиданно», код `20` — подтверждение нормализаций не автоматическое |
| `accept_cf.ps1` на одиночном модуле | `CheckModules` = `101` (нет общего модуля `УправлениеДоступом` из продукта) — ожидаемо, см. §8 |

Проверка на полном двухпоставочном комплекте (продукт + модуль, `.cf` ≈ 3,16 ГБ) выполнялась исходными
скриптами того же алгоритма: `LoadCfg` — 0 сообщений, `CheckModules` — без ошибок, `.bin` после цикла
совпал, обе копии с вендорскими SHA1, отличия от одноставочного эталона — только `.bin`,
`ConfigDumpInfo.xml` и копия модуля.
