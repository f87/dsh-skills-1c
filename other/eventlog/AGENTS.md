# AGENTS — правила раздела `other/eventlog`

Раздел хранилища [`skills-1c`](https://github.com/f87/dsh-skills-1c): журнал регистрации 1С —
формат `.lgp`/`.lgf`, разбор, загрузка в SQLite, анализ.
Общие правила хранилища — корневой [`AGENTS.md`](../../AGENTS.md); здесь — только специфика
раздела `other/eventlog`.

## 1. Статус и права

Права — по корневому [`AGENTS.md`](../../AGENTS.md) хранилища: изменения вносит администратор
хранилища или агент по его **прямому поручению**, остальные — только чтение и предложения
текстом. Внутри раздела это значит:

| Кто | Права |
|---|---|
| администратор хранилища и агент по его поручению | чтение, создание, изменение, удаление файлов `other/eventlog` |
| любой другой агент (в т. ч. запущенный в другом проекте) | **только чтение** и предложения текстом |

## 2. Запрет

**Без явного разрешения администратора хранилища запрещено:**

- создавать, изменять, переименовывать, перемещать и удалять любые файлы в разделе;
- менять структуру разделов и схему имён файлов (`<тема>.md`, скрипт рядом с документом);
- «улучшать» формулировки, переформатировать документы, менять порядок разделов;
- добавлять зависимости, внешние ресурсы и ссылки на конкретный проект;
- править `README.md`, `AGENTS.md`, `.gitignore` и `.gitattributes`.

**Разрешено без разрешения:** читать, цитировать, ссылаться, выполнять скрипты и примеры
на **копиях** данных.

## 3. Как вносится изменение

1. **Проверка.** Новый факт подтверждается прогоном на реальном файле (команда + результат +
   дата), а не «по памяти». Непроверенное — явно помечается «гипотеза» с описанием
   эксперимента, который её закроет.
2. **Место.** Факт кладётся в существующий файл своего раздела; новый файл — только если тема
   не покрыта. Тогда обновляются `README.md` (разделы, инструменты, «Что проверено»).
3. **Пометка.** В тексте указывается, что и когда проверено: «проверено 18.11.2026, срез 64 МиБ».
4. **Универсальность.** Никаких путей, имён баз и серверов конкретного проекта; примеры
   обезличены (`<файл.lgp>`, `<logdir>`, `<ib>`, `<значение>`), конфигурационно-специфичное —
   с пометкой «пример».
5. **История.** Устаревшее не удаляется молча: «ранее считалось …, проверено …, верно …».
   Ошибочное исправляется с указанием причины.

## 4. Стиль документов

Единый для раздела:

- заголовок `#` — тема; сразу под ним строка `Когда применять: …` и строка «Проверено …»;
- разделы `##` без нумерации, короткие абзацы, таблицы вместо перечислений;
- советы и ловушки — в таблице «Грабли» с колонками «Симптом / Причина / Решение»;
- проверяемое — блоком «Проверка» с командами, которые действительно выполнялись;
- ссылки между документами относительные, в квадратных скобках.

## 5. Скрипты

- все пути — аргументами, ничего не зашито;
- только стандартная библиотека Python (`sqlite3` входит в неё) — внешних зависимостей нет;
- каждый скрипт печатает, что прочитал и сколько записей разобрал (`read_record.py` печатает
  саму запись, а предупреждения — в stderr);
- коды возврата: `0` — успех, `1` — были неразобранные записи / запись не дочитана /
  не сошлось число строк с `--expect`, `2` — вход не тот (нет файла, не тот формат,
  смещение вне файла);
- русский текст в выводе не должен падать на консоли без кириллицы: скрипты переводят
  stdout/stderr в UTF-8 (`sys.stdout.reconfigure`).

## 6. Что должно быть проверено при изменении

| Изменение | Минимальная проверка |
|---|---|
| Парсер | прогон на файле ≥ 1 ГБ: неразобранных 0, независимый счётчик совпадает |
| Формат полей | выгрузка одной записи по `off` и сверка полей глазами |
| Схема базы | загрузка, `COUNT(*)` = число маркеров, выборочный `SELECT` по индексу |
| Рецепт анализа | запрос выполняется на загруженной базе и не падает |
| Документ | ссылки открываются, примеры команд запускаются, числа совпадают с прогоном |

## 7. Как сообщить о дефекте

```
файл: <путь>:<строка>
было: <точный фрагмент>
стало: <предлагаемый фрагмент>
почему: <что не так — неверный факт / потеря данных / битая ссылка / опечатка>
проверено: <чем — прогон, объём файла, дата>
```

## 8. Чего в разделе быть не должно

- утверждений о платформе без прогона (кроме явных «гипотеза»);
- проектных артефактов: баз, дампов, выгрузок, логов, `.lgp`/`.lgf` (для них — `.gitignore`);
- дублирования: если тема раскрыта в соседнем файле — ссылка, а не копия;
- примеров с реальными именами серверов, баз и GUID объектов.

## 9. Структура

```
other/eventlog/
  README.md        — карта раздела, инструменты, быстрый старт, что проверено
  AGENTS.md        — этот регламент
  format.md        — формат .lgp/.lgf, поля записи, поле «Данные»
  parsing.md       — нарезка записей, два уровня разбора, проверка полноты
  large-files.md   — десятки гигабайт: блоки, смещения, скорость, возобновление
  sqlite.md        — база SQLite: схема, load_sqlite.py, замеры, рецепты
  analysis.md      — методика анализа: разрезы, связки, знаменатель
  parse_lgp.py     — парсер журнала (CSV/TSV, --check)
  parse_lgf.py     — парсер справочника (JSON, SQL, --sqlite)
  read_record.py   — запись по off + src
  load_sqlite.py   — загрузка в SQLite (единственная СУБД раздела)
  .gitignore       — данные журнала и артефакты разбора не попадают в хранилище
  .gitattributes   — единые окончания строк LF
```

## 10. Версионирование

- Раздел лежит в хранилище `skills-1c`: коммит делается в клоне хранилища, своего `.git`
  у `other/eventlog` нет.
- Коммит — после проверок из §6, одним набором: `git add other/eventlog` →
  `git commit -F <файл-с-сообщением>`. Сообщение: что изменилось и чем проверено
  (объём, дата), как в §3.
- В коммит попадают только документы и скрипты: `.lgp`/`.lgf`, базы, TSV/CSV, `dict.sql`,
  `lgf.json` закрыты `.gitignore` раздела.
- Путь в репозитории: `other/eventlog/`; публикация — коммит в `master` хранилища.
