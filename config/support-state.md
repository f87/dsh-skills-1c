# Состояние поддержки в XML-выгрузке: где лежит и как менять

Универсально для любой конфигурации на поддержке. Проверено на 8.3.27.1859; `version="2.20"` — версия формата выгрузки 8.3.27, у другой версии платформы проверяйте фактический атрибут `version`.
Речь о правке **файлов выгрузки**, а не Конфигуратора: результат затем загружается
`LoadConfigFromFiles` (см. [`load-from-xml.md`](load-from-xml.md)).

Инструмент: [`support-state.ps1`](support-state.ps1) — просмотр, правка, сравнение с поставкой.

---

## 1. Где хранится состояние

| Файл | Что содержит |
|---|---|
| `Ext\ParentConfigurations.bin` | **уровень поддержки каждого объекта** + флаг конфигурации, по каждой поставке |
| `ConfigDumpInfo.xml` | реестр `uuid → полное имя объекта` (нужен, чтобы читать `.bin`; сам `.bin` хранит uuid) |
| `Ext\ParentConfigurations\<ИмяПоставки>.cf` | копия конфигурации поставщика. Есть, когда не полная поддержка; при полной — 1С её не выгружает |
| `*.xml` объектов | **состояния поддержки не содержат** |

Проверка на двух выгрузках одной конфигурации («на замке» и «возможность изменения включена»):
все 12 704 файла совпали побайтно, кроме `ConfigDumpInfo.xml` и `Ext\ParentConfigurations.bin`.
Значит, менять поддержку = править `.bin` (+ копию `.cf`), а не XML объектов.

> В `.bin` есть и записи объектов, которых в конфигурации уже нет (переименованы/удалены) — это норма;
> и нет записей собственных объектов — им поддержка не нужна.

---

## 2. Формат `Ext\ParentConfigurations.bin`

Текст, UTF-8 **с BOM**, **одна строка**, значения через запятую, кавычки внутри строки удваиваются.
Порядок и число токенов менять нельзя — только значения.

### Блок поставки

```
{6,<флаг>,<кол-во поставок>,<guid поддержки>,
 <флаг>,<guid>,<версия>,<поставщик>,<имя поставки>,<кол-во объектов>,
 <уровень>,<режим>,<uuid>,<uuid в поставке>,   × N
 <2 служебных токена>,
 <следующая поставка> ...
```

Индексы для **первой** поставки: `0 = "{6"`, `1 = флаг`, `2 = число поставок`, `3 = guid поддержки`,
`4 = флаг (дубль)`, `5 = guid`, `6 = версия`, `7 = поставщик`, `8 = имя`, `9 = объектов`, `10… = объекты`.
Блок каждой следующей поставки начинается со смещения `start + 9 + 4·N` и имеет ту же структуру
(свой `guid`, флаг, версия, поставщик, имя, счётчик).

### Запись объекта — 4 токена

| Смещение | Значение |
|---|---|
| +0 | уровень: `0` — не редактируется (на замке); `1` — с сохранением поддержки; `2` — снят с поддержки |
| +1 | режим поставки: `0` — изменения разрешены (обычно), `1` — не рекомендуются, `2` — запрещены |
| +2 | uuid объекта |
| +3 | uuid объекта в поставке (в основной поставке совпадает с +2) |

Хвост файла (после последней поставки) — служебные флаги обновления, трогать не нужно.

### Несколько поставок: уточнения формата

Проверено 8.3.27.1859, 28.10.2026 на одиннадцати файлах (живая база с двумя поставками, одноставочные
вендорские и производные, пять собранных вручную двухставочных).

```
{ "6", flag, count, supportGuid,
  d0:                 flag, guid, "ver", "vendor", "name", N, (lvl, mode, uuid, uuidIn)×N, "0", "0",
  d1: parentGuid, flag, guid, "ver", "vendor", "name", N, (lvl, mode, uuid, uuidIn)×N, "0", "0",
  …
  tail: 3 служебных токена + по 10 чисел на поставку (последнее — с «}»)
```

- `parentGuid` **первой** поставки отдельным токеном не пишется: им служит `supportGuid` заголовка
  (токен 3). Поэтому в любом корректном файле `d0.parentGuid == supportGuid` — это наблюдение, а не
  доказанное требование 1С (файл с любым `supportGuid` 1С принимает молча).
- Блок поставки: `9 + 4·N` токенов; `tailStart = 3 + Σ(9 + 4·N)`. Хвост: `3 + 10` чисел на поставку
  (1 поставка — 13 токенов, 2 — 23). Назначение полей хвоста неизвестно; 1С **возвращает его без
  изменений** после цикла загрузка → выгрузка.
- `mode` в наблюдавшихся файлах — `0` везде, кроме 23 записей поставки модуля (`1`).
- `uuidInDelivery` может отличаться от `uuid`.
- Записи одного UUID допустимы в **разных** поставках (в живой базе — 4 565 общих UUID). Это норма.
- Порядок поставок и число копий — конвенция и следствие флагов, см.
  [`supply/deliveries.md`](supply/deliveries.md): главная поставка первой, `flag=0` обеим.

### Проверка, что вы поняли файл правильно

`N` из заголовка должно совпадать с числом разобранных записей, а последний токен — заканчиваться `}`.
Скрипт делает это автоматически и предупреждает, если «сборка токенов обратно» не совпала с файлом.

## 3. Числа состояний

| Что | Значение |
|---|---|
| флаг конфигурации (`1` и `4`) = 1 | изменения запрещены — полная поддержка/замок |
| флаг = 0 | возможность изменения включена |
| уровень 0 | объект не редактируется = «на поддержке» |
| уровень 1 | редактируется с сохранением поддержки (правки отслеживаются относительно поставки) |
| уровень 2 | снят с поддержки (не поддерживается поставщиком) |

Что делает Конфигуратор (проверено побайтным сравнением с выгрузками):

| Действие | Флаг | Уровни |
|---|---|---|
| «Включить возможность изменения» у **конфигурации** | `1 → 0` | **всем** `1 → 0` |
| «Полная поддержка»/замок | `0 → 1` | **всем** `0 → 1` |
| «Разрешить изменение» у **объекта** | — | `0 → 1` (только у него) |
| «Снять с поддержки» у объекта | — | `→ 2` |

Поэтому «на замке» — это флаг, а не массовая установка уровней; в режиме замка уровни объектов не действуют.

> **Правило для собранных конфигураций:** используем только `0` и `1`; `2` — исключение по прямому
> указанию владельца. Объект, побайтно совпадающий с поставкой → `0`; любое отличие (включая изменённый
> или новый реквизит ТЧ) → `1`. Корень `0` только если все дочерние записи `0`. Как считать —
> [`supply/support-levels.md`](supply/support-levels.md).

## 4. Процедуры

### 4.1. Диагностика

```powershell
pwsh -File support-state.ps1 -Tree <tree>
pwsh -File support-state.ps1 -Tree <tree> -ObjectName 'Catalog.Номенклатура'
pwsh -File support-state.ps1 -Tree <tree> -All            # все объекты поставки
```

Вывод: поставки (имя/версия/вендор/флаг) и распределение уровней.

### 4.2. Снять общий замок (разрешить изменения в конфигурации)

```powershell
pwsh -File support-state.ps1 -Tree <tree> -EnableChanges
```

### 4.3. Разрешить правку конкретного объекта

```powershell
# «редактируется с сохранением поддержки»
pwsh -File support-state.ps1 -Tree <tree> -ObjectName 'Document.Заказ' -Level 1

# «снят с поддержки» — если объект правится надолго и обновлять его не планируется
pwsh -File support-state.ps1 -Tree <tree> -ObjectName 'Document.Заказ' -Level 2

# пакетно, из файла (по одному имени в строке, # — комментарий)
pwsh -File support-state.ps1 -Tree <tree> -ObjectsFromFile .\off-support.txt -Level 2
```

Имена — как в `ConfigDumpInfo.xml`: `Catalog.X`, `Document.X.Attribute.Y`, `InformationRegister.X.Resource.Z`.
У объекта — все его изменяемые части (реквизиты, формы, ресурсы, команды) учитываются отдельными записями.

### 4.3.1. Пакетная правка уровней (тысячи записей)

`support-state.ps1 -ObjectsFromFile` перебирает все записи поставки на каждое имя: на 7 000+ имён это
практически висит. Для массовых операций — прямые инструменты (секунды):

```powershell
# 1) развернуть корневые имена в полные записи .bin (реквизиты/формы/ресурсы)
node config\support\expand_names.js <bin> <ConfigDumpInfo.xml> roots.txt full.txt
# 2) выставить уровень (без --apply — только отчёт)
node config\support\set_levels.js <bin> <ConfigDumpInfo.xml> full.txt 2 --apply
# 3) флаги конфигурации/поставок
node config\support\set_flags.js <bin> 0 0 --apply
# 4) разобрать структуру файла (только чтение)
node config\support\inspect_bin.js <bin> <ConfigDumpInfo.xml>
```

Порядок важен: сначала изменённые (`1`), затем снятые (`2`), затем корень — иначе более поздняя установка
перезапишет уровень. `support-state.ps1` остаётся инструментом проверки и точечных правок.

Для **собранной** конфигурации уровни не задают вручную и не копируют из базы: их считает
[`supply/support-levels.js`](supply/support-levels.md) по отличиям дерева от дерева поставки. `set_levels.js`
остаётся для точечных правок и для случаев, когда правило 0/1 неприменимо (например, нужно принудительно
снять объект с поддержки).

### 4.4. Вернуть объект на поддержку

Условие: файлы объекта **побайтно** совпадают с поставкой. Проверка:

```powershell
pwsh -File support-state.ps1 -Tree <tree> -Compare <vendor tree>
```

Если отличий нет:

```powershell
pwsh -File support-state.ps1 -Tree <tree> -ObjectName 'Catalog.Номенклатура' -Level 0
```

Если объект возвращается целиком на полную поддержку — сначала верните все его файлы к версии поставки
(включая удаление своих реквизитов/форм/модулей), затем `-Level 0`; для конфигурации целиком — `-Lock`.

> При снятии с полной поддержки 1С хранит копию поставки в `Ext\ParentConfigurations\<ИмяПоставки>.cf`.
> Если в дереве этого каталога нет, а объекты уже не на полной поддержке — скопируйте `.cf` из эталонной
> выгрузки той же поставки (иначе Конфигуратор может запросить файл поставки при сравнении/восстановлении).

### 4.5. Правка корня конфигурации

Корень — первая запись поставки, имя `Configuration.<ИмяКонфигурации>`:

```powershell
pwsh -File support-state.ps1 -Tree <tree> -ObjectName 'Configuration.УправлениеПредприятием' -Level 1
```

Нужно, когда менялись свойства корня или состав объектов (`Configuration.xml`) — например, добавлен свой
объект. Свойства — в [`edit-xml.md`](edit-xml.md), §6.

## 5. Проверка результата

Минимум (без Конфигуратора) — повторная выгрузка из базы и сверка:

```powershell
$exe = '<путь>\1cv8.exe'
Remove-Item <ib> -Recurse -Force -ErrorAction SilentlyContinue
New-Item -ItemType Directory -Force <ib> | Out-Null
& $exe CREATEINFOBASE "File='<ib>'" /Out"<log>\create.log" /DisableStartupDialogs /DisableStartupMessages
& $exe DESIGNER /F"<ib>" /LoadConfigFromFiles"<tree>" /Out"<log>\load.log" /DisableStartupDialogs /DisableStartupMessages
& $exe DESIGNER /F"<ib>" /DumpConfigToFiles"<dump>" /Out"<log>\dump.log" /DisableStartupDialogs /DisableStartupMessages
```

Ожидание:

- `LoadConfigFromFiles` — EXIT 0, в логе «Загрузка конфигурации успешно завершена»;
- `Ext\ParentConfigurations.bin` в `<dump>` **побайтно равен** вашему (1С сохраняет выставленные уровни);
- остальные файлы дерева — 0 отличий; `ConfigDumpInfo.xml` отличается **только** `configVersion`
  (1С пересчитывает его сама; устаревшие значения загрузке не мешают — проверено);
- в Конфигураторе: `Конфигурация → Поддержка → Настройка поддержки` — состояния совпадают с задуманным.

Запуск 1С — только вне файловой песочницы; см. [`../1cv8/launch-modes.md`](../1cv8/launch-modes.md)
и [`../1cv8/cli-gotchas.md`](../1cv8/cli-gotchas.md).

## 6. Ошибки

| Симптом | Причина / что делать |
|---|---|
| 1С ругается на `ParentConfigurations.bin` | побились кавычки, BOM или переводы строк. Откатить файл, править только скриптом |
| «Несовпадение версии», инкрементальные ошибки при загрузке | устаревший `ConfigDumpInfo.xml`: удалить его из дерева и загрузить снова либо пересобрать выгрузку |
| Объект не становится редактируемым | флаг конфигурации = 1 → `-EnableChanges` |
| 1С не предлагает «поставить на поддержку» | файлы объекта отличаются от поставки (`-Compare`) или нет `Ext\ParentConfigurations\<Имя>.cf` |
| В `.bin` несколько поставок, объект нашёлся не с первого раза | имя может встречаться в нескольких поставках; уровень ставится в записи, соответствующей uuid из `ConfigDumpInfo` |
| «Нет в поставке» для своего объекта | объект добавлен вами — записи в `.bin` нет, менять нечего |

Связанное: [`support.md`](support.md) — постановка/снятие через Конфигуратор, два поставщика, ограничения `.cfu`;
[`xml-format.md`](xml-format.md) — общий формат выгрузки.
