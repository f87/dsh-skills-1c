# Жёсткие правила работы с XML-выгрузкой 1С

Инварианты, нарушение которых даёт нерабочий `.cf` или «немодифицируемую» конфигурацию.
Универсально для любой конфигурации 8.3 и любой версии платформы 8.3.27.* и ниже; проверено на 8.3.27.1859. Подробности — в
[`support-state.md`](support-state.md) и [`edit-xml.md`](edit-xml.md).

## R01. Состояние поддержки живёт не в объектах

`*.xml` объектов **не содержат** признака поддержки. Оно целиком в `Ext\ParentConfigurations.bin`
(уровни объектов + флаг конфигурации), имена — из `ConfigDumpInfo.xml` по `uuid`.
Проверено: две выгрузки одной конфигурации, отличающиеся только поддержкой, побайтно равны по всем
файлам объектов.

## R02. `.bin` правится только скриптом

Одна строка, UTF-8 **с BOM**, значения через запятую, кавычки удваиваются. Менять можно **только
значения**, не порядок и не число токенов. Инструмент — [`support-state.ps1`](support-state.ps1).

## R03. Числа состояния

- флаг конфигурации `1` — изменения запрещены (полная поддержка/замок), `0` — возможность изменения включена;
- уровень `0` — не редактируется (на поддержке); `1` — с сохранением поддержки; `2` — снят с поддержки;
- `режим поставки` обычно `0`.

## R04. Массовые операции повторяют 1С побайтно

«Включить возможность изменения» = флаг `1→0` **и** всем объектам `1→0`; «полная поддержка» = флаг `0→1`
**и** всем объектам `0→1`. Проверено сравнением SHA1 с выгрузками Конфигуратора.

## R05. Править объект можно только сняв замок

Сначала снять флаг (`-EnableChanges`), затем уровень объекта `1` или `2`. Иначе 1С считает объект
неизменяемым.

## R06. На поддержку ставится только побайтно идентичный объект

Уровень `0` допустим, лишь когда файлы объекта совпадают с поставкой — проверка `-Compare <vendor tree>`
даёт 0 отличий. Свои реквизиты/формы/модули объекта должны быть удалены.

## R07. Свои объекты в `.bin` отсутствуют

Добавленные вами объекты записи не имеют — менять нечего. Записи удалённых/переименованных объектов
(«мёртвые» `uuid`) — норма.

## R08. Новый элемент — свежий `uuid` и своя группа

`[guid]::NewGuid()`, уникальный в дереве. Вставка в **конец группы своего типа** в `<ChildObjects>`
(документ/справочник: `Attribute → Form → TabularSection → Command`; регистр: `Resource → Attribute → Dimension`).
Запись в `ConfigDumpInfo.xml` обязательна.

Скрипты хранилища (`config\update\addchild.js`, `config\update\objmerge.js`) добавляют элементы **в конец всего**
`<ChildObjects>`: 1С это принимает, но её выгрузка переставит элементы — для побайтных диффов после
прогона скриптов элементы можно переставить в свои группы.

## R09. Новый объект регистрируется в трёх местах

Файл `<Каталог>\<Имя>.xml` (5 пар `TypeId`/`ValueId` + `uuid`), строка в `Configuration.xml` в конец группы
своего типа, запись в `ConfigDumpInfo.xml`. В подсистему — через `<Content>` с `xr:MDObjectRef`.

## R10. `configVersion` не пересчитываем

Это хэш 1С. Устаревшие значения загрузке не мешают (проверено), 1С пересчитает их при выгрузке.
Не собирать `ConfigDumpInfo.xml` вручную целиком.

## R11. Запуск 1С

- только вне файловой песочницы (в ограниченной — падение `NullReferenceException … SCOM_Main`, код `-532462766`);
- `CREATEINFOBASE "File='<ib>'"` — форма с удвоенными кавычками `""` в pwsh 7 ломается;
- свитч и путь слитно: `/F"<ib>"`, `/LoadConfigFromFiles"<tree>"`, `/DumpConfigToFiles"<tree>"`, `/Out"<log>"`;
- stdout не читается: статус — из `/Out`-лога, код возврата — `Start-Process -Wait -PassThru → ExitCode`.

## R12. Проверка обязательна

`LoadConfigFromFiles` EXIT 0 → `DumpConfigToFiles` → `ParentConfigurations.bin` **совпал побайтно**,
остальное дерево — 0 отличий (`ConfigDumpInfo.xml` отличается только `configVersion`) → при сборке `.cf`
контрольная `LoadCfg` в чистую базу EXIT 0.

## R13. Чего не делать

- не менять `<Version>` конфигурации (остаётся версия поставки);
- не править роли поставщика — права на свои объекты отдельными ролями;
- не восстанавливать удалённые поставщиком объекты «для совместимости» — чистить ссылки;
- не «оптимизировать» `.bin` и `ConfigDumpInfo.xml` вручную.

## R14. Байтовая точность

UTF-8 **с BOM**, CRLF, **без** перевода строки в конце файла. `Set-Content`/`WriteAllLines` добавляют
хвостовой `CRLF` — обрезайте, если сверяете SHA1.

## R15. `.cf` — не эталон сравнения

`DumpCfg` детерминирован внутри одной базы, но две разные базы из одного дерева дают `.cf` с **разными
MD5** при идентичном содержимом. Сравнивайте конфигурации по XML и `.bin`; MD5 `.cf` — идентификатор
сборки (фиксируйте вместе с датой).

## R16. Замок перекрывает уровни

В режиме полной поддержки (флаг `1`) 1С пишет всем объектам уровень `1`; реальный запрет задаёт флаг.
Поэтому «на замке» — это `-Lock`, а не поштучная установка уровней.

## R17. Несколько поставок в `.bin` — норма

`ParentConfigurations.bin` с несколькими поставками 1С **принимает** и сохраняет байт-в-байт (ранее
считалось, что не принимает; проверено 28.10.2026 — те сообщения давали висячие ссылки дерева, а не
число поставок). Правила:

- главная поставка — **первая**: совпадение `name`+`version` с `Configuration.xml`, иначе вендор
  продукта; её `parentGuid` = заголовочный `supportGuid`;
- `flag=0` **каждой** поставке, чья копия `.cf` нужна (`flag=1` — 1С копию удаляет при загрузке);
- копия `*.cf` — **байтовая** копия вендорского файла (сверять SHA1);
- содержимое конфигурации от числа поставок не зависит: отличия от одноставочного эталона — только
  `.bin`, `ConfigDumpInfo.xml` и добавленная копия;
- приёмка — `LoadCfg` → `CheckModules -ThinClient -Server` → выгрузка → сверка `.bin` и копий, а не код
  возврата `LoadCfg`.

Подробности: [`supply/deliveries.md`](supply/deliveries.md), [`supply/which-is-main.md`](supply/which-is-main.md),
процедура — [`supply/build-and-check.md`](supply/build-and-check.md).

## R18. Ни один поставщик не теряется при обновлении

Сколько поставок в `Ext\ParentConfigurations.bin` было до обновления — столько должно остаться после;
менять можно только **порядок** (главная — первой). Дерево, у которого в `.bin` меньше поставок, при
`LoadConfigFromFiles` **молча** затирает остальные: exit 0, сообщений нет, а объекты пропавшей поставки
перестают быть поддержанными (проверено 28.10.2026, 8.3.27.1859 — прямая загрузка одноставочного дерева
поверх двухпоставочной базы: было 2, стало 1, `.bin` совпал с одноставочным исходником).

Проверки: `config\supply\bin_summary.js` до загрузки и после выгрузки, `config\supply\bin_diff.js` для
сверки состава, копии `*.cf` — по одной на поставку с `flag=0`. Правило и восстановление —
[`update/deliveries-invariance.md`](update/deliveries-invariance.md).

## R19. Уровни поддержки в собранной конфигурации — только `0` и `1`

Уровень `2` не используем (исключение — прямое указание владельца): он выключает объект из
автоматического обновления поставщика. Объект, побайтно равный поставке → `0`, любое отличие → `1`;
корень `0` только если все дочерние записи `0`; правка реквизита ТЧ делает `1` у ТЧ и у документа.
Уровни **считаются** инструментом, а не копируются из базы заказчика — иначе статус корня разносится
на всё поддерево (проверено 29.10.2026, 8.3.27.1859: из 8 230 записей `2` — 5 478 были чужими детьми).

Инструмент: [`supply/support-levels.js`](supply/support-levels.md); гейты 17/18 в
[`update/acceptance.md`](update/acceptance.md); точечные правки — [`support-state.md`](support-state.md) §4.3.

## R20. Состав поставок задаёт исходная конфигурация, а не инструкция сборки

Сколько поставок в рабочей базе или эталоне (и сколько копий `*.cf` в `Ext\ParentConfigurations\`),
столько должно быть в собранном `.bin`. Одноставочная сборка из двухпоставочного исходника — дефект
сборки, а не «допущение» ([`update/deliveries-invariance.md`](update/deliveries-invariance.md)). Гейт ставится
**до** загрузки: `bin_summary.js` собранного `.bin` против исходного.

## R21. Проверенный факт коллекции важнее инструкции проекта

Промт, чек-лист или `SKILL` проекта могут содержать утверждение, которое коллекция уже опровергла
(пример: «две поставки 1С не принимает» — [`update/traps.md`](update/traps.md) п.17). Приоритет — у факта
с пометкой «проверено»; расхождение **останавливает** работу: сначала правят инструкцию (в той же задаче),
потом делают по ней. Молча исполнять устаревшую инструкцию — значит повторить ошибку и потерять данные.
