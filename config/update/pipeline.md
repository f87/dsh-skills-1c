# Конвейер сборки обновлённой конфигурации

Реализация: пример конвейера — `<проект>\_work\scripts\build_v1.ps1` (конкретный проект ERP 2.5.27.98);
универсальные инструменты шагов лежат в `config\update\*.js`. Ниже — что и в каком порядке делать,
чтобы результат загружался и не терял данные.

## Вход

- `src\update_erp` — поставка (новая версия, например 2.5.27.98);
- `src\current` — текущая конфигурация с доработками;
- `src\vendor_erp` — предыдущая версия поставки (для 3-стороннего слияния);
- манифесты: `objects_update_erp.json`, `objects_current.json`, `objects_vendor_erp.json`;
- списки: объекты current, отсутствующие в поставке; удалённые поставщиком.

## Шаги

1. **Копия поставки** → `result_v1` (`robocopy /MIR`), переименовать `ConfigDumpInfo.xml` → `.bak`.
2. **Каркас**: скопировать объекты current, которых нет в поставке (`config\update\skel.js`), добавить их в
   `ChildObjects` (`addchild.js`). Не копировать удалённые поставщиком — список исключений передаётся в `skel`.
3. **Предопределённые** — только 2 каталога (`regmerge.js predefined`): наборы доп. реквизитов и
   идентификаторы объектов метаданных.
4. **Определяемые типы — объединение с приоритетом current** (`mergetypes.js --apply`), затем контрольный
   dry-run: `addedFromCurrent = 0`. **Без этого шага сборка непригодна** (`defined-types.md`).
5. **Переименования реквизитов** (`Удалить…`): переименовать ссылки (`renamerefs.js`), не добавлять дубли.
6. **Наш регистр** зарегистрировать в документе-регистраторе (`addregrec.js`).
7. **Элементы объектов поставщика**: `objmerge.js` + `syncobjfiles.js` (формы/макеты/файлы).
8. **Модули**: `blockmerge.js` (см. `merge-modules.md`), затем маркеры `{УАТ}` вокруг заменённых процедур.
9. **Инвариант дельты** — до загрузки, дешёвая проверка: `node config\update\delta-check.js <beforeTree>
   <result> <vendor…>` → `lost = 0`, `new = 0`; `removed` — только удалённое поставщиком и в отчёт
   (`delta-invariance.md`). Если `lost`/`new` не нулевые — чинить слияние, а не отчёт.
   Там же — **состав поставок**: `node config\supply\bin_summary.js <result>\Ext\ParentConfigurations.bin`,
   `count` и пары `name`+`version` совпадают с исходным `.bin`; собрать меньше поставок, чем было, нельзя
   (`deliveries-invariance.md`, R20).
10. **Загрузка** в пустую базу → классификация лога → `CheckModules -ThinClient -Server` → `DumpCfg` →
    контрольная загрузка (`acceptance.md`).

## Ожидаемые объёмы (пример ERP 2.5.27.98)

| Показатель | Значение |
|---|---|
| объектов скопировано из current | 1 516 (1 463 верхнеуровневых + 53 вложенных подсистемы) |
| записей `ChildObjects` | 22 351 → 23 815 |
| предопределённых добавлено | +229 |
| **определяемых типов добавлено** | **890 в 38 типах** |
| модулей слито | 34 |
| процедур заменено целиком | 4 |

## Почему такой порядок

- Типы объединяются до слияния модулей: `mergetypes` фильтрует типы по наличию объекта в дереве, а каркас
  уже создан.
- `objmerge` идёт после типов, чтобы вставленные элементы не потерялись при перезаписи файлов.
- Загрузка — только после всех правок: каждая итерация 38–49 мин, поэтому дешевле сначала прогнать
  дешёвые проверки (типы, XML-валидность, ссылки).

## Грабли

- Не запускайте сборку на дереве, которое загружается в 1С.
- Не перезаписывайте объекты поставки версиями current (потеряются изменения поставщика).
- `ConfigDumpInfo.xml` в рабочем дереве держат удалённым/переименованным для чистоты и воспроизводимости.
  Проверено 20.10.2026 (8.3.27.1859): это **не обязательное условие** — полная `LoadConfigFromFiles`
  перечитывает файлы и при устаревших `configVersion` (изменение применяется, версия пересчитывается).
