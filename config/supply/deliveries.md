# Несколько поставок в одной конфигурации

Универсально: любая конфигурация 8.3, где в одной базе сосуществуют **несколько поставок поставщика**
(основной продукт + отраслевой модуль, дополнение, «для 1С:ERP» и т. п.).
Проверено 8.3.27.1859, 28.10.2026.

Формат файла и поштучные процедуры — [`support-state.md`](../support-state.md) §2; где лежат копии
поставок и как считать дельту — [`vendor-configs.md`](../vendor-configs.md); порядок сборки —
[`which-is-main.md`](which-is-main.md); процедура и приёмка — [`build-and-check.md`](build-and-check.md).

Если это поставки **обновляемой** конфигурации — состав поставок при обновлении сохраняется:
[`deliveries-invariance.md`](../update/deliveries-invariance.md).

---

## 1. Ранее считалось (исправлено)

> «`.bin` с двумя поставками 1С не принимает: 196 “Тип предопределённого вида характеристики не
> соответствует типу плана” + 4 “Неизвестный объект”».

**Проверено 28.10.2026: неверно.** Те же сообщения воспроизводятся на **одноставочном** дереве, если в
нём есть висячие ссылки на удалённые поставщиком объекты (в проекте проверки — ссылки модуля на
объекты, удалённые в новой версии продукта). После чистки ссылок (`config/update/prunerefs.js`) двухставочный
`.bin` загружается **без единого сообщения**.

Вывод: **1С принимает несколько поставок и сохраняет `.bin` байт-в-байт** (проверено полным циклом
`LoadConfigFromFiles` → `DumpConfigToFiles`: SHA1 совпал с загруженным).

## 2. Правила

### 2.1. Главная поставка — первая

Порядок 1С не проверяет, поэтому он задаётся конвенцией: главная поставка первой, её `parentGuid` =
заголовочный `supportGuid`. Как определить главную — [`which-is-main.md`](which-is-main.md).

### 2.2. `flag=0` всем поставкам, копии которых нужны

| `flag` поставки | Что делает 1С при загрузке |
|---|---|
| `0` | копия `*.cf` этой поставки **остаётся** в `Ext\ParentConfigurations\` |
| `1` | копия **удаляется** |

Проверено: вариант с `flag=1` у второй поставки — после цикла копия второй поставки исчезла; с
`flag=0` у обеих — обе копии на месте. При нескольких поставках ставить `0` **обеим**, иначе потеряете
копию нужной поставки (и путь её обновления).

### 2.3. Копия — байтовая копия вендорского `.cf`

Копия в `Ext\ParentConfigurations\<Имя поставки>.cf` должна совпадать с вендорским файлом по SHA1.
«Похожий» файл, `.cf` другой версии и `.cf`, собранный из результата, — не копия поставки.

Если `flag=0`, а копии нет — загрузка падает: `Каталог не обнаружен …\<Имя>.cf`.

### 2.4. Содержимое конфигурации не зависит от числа поставок

Добавление второй поставки **не меняет ни один файл конфигурации**. Отличие результата от
одноставочного эталона — ровно три вещи:

- `Ext\ParentConfigurations.bin`;
- `ConfigDumpInfo.xml` (1С пересчитывает `configVersion`);
- добавленная копия `*.cf` второй поставки.

Проверено на дереве из 131 354 файлов: `потеряно 0, добавлен 1, изменено 2`.

### 2.5. Пересечения UUID между поставками нормальны

Одни и те же объекты могут входить в обе поставки (в живой базе проекта проверки — 4 565 общих UUID,
например `Subsystem.Администрирование`, `StyleItem.*`). 1С это принимает; вычищать имеет смысл только
при осознанном слиянии дублей.

### 2.6. Уровни — в семантике [`support-state.md`](../support-state.md) §3

`0` — не редактируется (на поддержке), `1` — редактируется с сохранением поддержки, `2` — снят.
Встречающаяся в чужих описаниях формулировка «`0` — не на поддержке» **неверна**; проверено побайтным
сравнением с выгрузками Конфигуратора.

### 2.7. Уровни в многопоставочном `.bin` считаются по каждой поставке

Уровни в `.bin` с несколькими поставками считает [`support-levels-multi.js`](support-levels.md) §3.1:
каждая запись сравнивается со своей поставкой, уровень главной поставки на записи второстепенных не
переносится. После `--write` проверять `bin_diff.js` до/после: состав записей и `mode` меняться не должны —
только уровни.

## 3. Что 1С проверяет, а что нет

| Свойство | Проверяет | Подтверждение |
|---|---|---|
| число поставок (`count`) и наличие каждой | да, по факту загрузки | загрузка без сообщений |
| `flag=0` ⇒ наличие копии `*.cf` | **да** | без копии — «Каталог не обнаружен» |
| совпадение `supportGuid` с вендорским | **нет** | файл с другим `supportGuid` загрузился молча |
| порядок поставок | **нет** | загружались оба порядка |
| `parentGuid` = вендорский `supportGuid` | **нет** | `parentGuid` = локальный guid базы |
| пересечение UUID между поставками | **нет** | 4 565 общих UUID в живой базе |
| сохранность файла после цикла | сохраняет | `.bin` после выгрузки идентичен загруженному |

Практическое следствие: проверять сборку нужно **не** на «1С не ругается», а на структуре `.bin`,
копиях и содержимом ([`build-and-check.md`](build-and-check.md) §5).

## 4. Что подтверждено экспериментом (пример проекта)

Пять вариантов `.bin`, собранных из двух одноставочных файлов (одно и то же дерево, 683 308 токенов,
170 816 записей — 159 954 продукта + 10 862 модуля):

| Вариант | Порядок | Заголовочный `supportGuid` | `flag` второй | Загрузка | Копии после цикла |
|---|---|---|---|---|---|
| A | продукт → модуль | продукта | `1` | exit 0 | только продукта (копия модуля удалена) |
| C | модуль → продукт | из живой базы | `0` | exit 0 | обе |
| E | продукт → модуль | продукта | `0` | exit 0 | обе |

A, C и E загрузились одинаково чисто (28 сообщений о висячих ссылках, свойственных дереву, «Ошибка» 0),
`.bin` после цикла у всех совпал с загруженным. Отсюда: **порядок и заголовочный guid 1С не сверяет,
флаг управляет копией.**

Варианты с переносом уровней по эталону (`adapt`) собирались, но не загружались — цель достигалась на
`vendor`-сборке. Приёмка обеих загруженных сборок: `.cf` ≈ 3,16 ГБ, `LoadCfg` — 0 сообщений,
`CheckModules` — без ошибок, выгрузка — те же 131 354 файла.

## 5. Гипотезы (не проверены)

1. Запись корня конфигурации (`Configuration.<uuid>`) во второй поставке может быть не нужна: в живой
   базе она была только у «своей» поставки (уровень `1`), у второй — с уровнем `2`. Собранные файлы
   содержат корень у обеих с уровнем `1`, 1С это принимает, но структура отличается от эталонной.
2. Штатное «Поддержка → Обновить» дополнения из двухпоставочной конфигурации не проверялось: нужен
   файл обновления следующей версии. Неизвестно, требуется ли для этого `parentGuid` = вендорский
   `supportGuid` (в сборках там локальный guid базы). Опыт, который закроет: применить `.cfu` новой
   версии модуля и посмотреть, предложит ли 1С обновление с сохранением правок.
3. Уровни в собранных файлах — реконструкция (вендорские либо перенос по UUID из эталона), а не расчёт
   самой 1С.

## 6. Грабли

| Симптом | Причина | Что делать |
|---|---|---|
| копия второй поставки исчезла после загрузки | у неё `flag=1` | пересобрать с `flag=0` |
| «Каталог не обнаружен `…\<Имя>.cf`» | `flag=0`, копии нет | положить байтовую копию вендорского `.cf` |
| «196 “Тип предопределённого вида характеристики…”» | висячие ссылки на удалённые объекты | чистить ссылки (`config/update/prunerefs.js`), а не число поставок |
| «Неизвестный объект метаданных — `Configuration.<Имя модуля>`» | в правах/планах остались ссылки на корень дополнения | свойство дерева; на содержимое `.cf` не влияет, лучше вычистить |
| `.bin` отличается от ожидаемого по SHA1 | другой источник уровней (вендорский vs. перенесённый по эталону) | сверять структуру (`bin_diff.js`), а не только SHA1 |
| 1С «не видит» вторую поставку | в файле `count=1` или поставка без записей | пересобрать; сборщик проверяет `count` и `N` |
