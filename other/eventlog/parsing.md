# Разбор записей журнала

Когда применять: пишешь свой парсер или проверяешь чужой, и нужно не потерять записи
на объёме в десятки гигабайт.

Проверено на журнале платформы 8.3 (формат `1CV8LOG(ver 2.0)`), 198,3 млн записей:
после двухуровневого разбора неразобранных записей 0.

## Почему нельзя резать по строкам

Запись переменной длины и может занимать десятки строк: комментарий со стеком вызова
содержит переводы строк внутри кавычек. Правила платформы при записи:

1. открывающей `{` **начала записи** всегда предшествует перевод строки
   (во вложенных структурах `{` идёт после запятой — `{"P",\n{518,…`);
2. закрывающие `}` не идут подряд — между ними всегда `\n`;
3. перевод строки может встречаться **внутри кавычек**.

Признаки корректной записи: начинается с `{`, заканчивается `}`, число `{` равно числу `}`,
число кавычек чётное.

## Надёжный признак начала записи

```
\n{<ровно 14 цифр>,
```

Строки стека внутри комментария тоже начинаются с `{`
(`{ОбщийМодуль.КалендарныеГрафики.Модуль(478)}:…`), но там нет 14 цифр — якорь с датой
не даёт ложных срезов.

```python
REC = re.compile(rb"\n\{(\d{14}),")
```

## Два уровня разбора

### Уровень 1 — одна регулярка на всю запись

Покрывает практически всё и примерно втрое дешевле посимвольного разбора.

```python
HEAD = re.compile(
    rb"\n\{\s*(\d{14}),\s*([A-Z]),\s*\{([0-9a-f]+),([0-9a-f]+)\},\s*"
    rb"(\d+),\s*(\d+),\s*(\d+),\s*(\d+),\s*(\d+),\s*([A-Z]),\s*"      # дата … важность
    rb'"((?:[^"]|"")*)"\s*,\s*(\d+)\s*,\s*'                          # комментарий, метаданные
    rb'(\{(?:[^{}]|\{(?:[^{}]|\{[^{}]*\})*\})*\})\s*,\s*'            # Данные (до 3 уровней)
    rb'"((?:[^"]|"")*)"\s*,\s*(\d+),\s*(\d+),\s*(\d+),\s*(\d+)'      # представление, сервер, порты, сеанс
)
```

Группы: 1 дата, 2 статус, 3–4 транзакция, 5 пользователь, 6 компьютер, 7 приложение,
8 соединение, 9 событие, 10 важность, 11 комментарий, 12 метаданные, 13 данные,
14 представление, 15 сервер, 16 основной порт, 17 вспомогательный порт, 18 сеанс.

### Уровень 2 — разбор по скобкам

Структура вида `{"P",{65534,{"A",{10,{"O",{"#",…}}}}}}` имеет 5+ уровней вложенности,
регулярка выше её не берёт и запись **молча выпадает**. На проверенном журнале так
терялось 2 625 записей из 198,3 млн (0,0013 %) — в том числе все `_$User$_.Update`.

```python
def fields(b):
    toks, i, n, depth, inq, start = [], 0, len(b), 0, False, 1
    while i < n:
        c = b[i]
        if inq:
            if c == 0x22:
                if i + 1 < n and b[i + 1] == 0x22:
                    i += 2
                    continue
                inq = False
            i += 1
            continue
        if c == 0x22:
            inq = True
        elif c == 0x7B:
            depth += 1
        elif c == 0x7D:
            depth -= 1
            if depth == 0:
                toks.append(b[start:i])
                return toks
        elif c == 0x2C and depth == 1:
            toks.append(b[start:i])
            start = i + 1
        i += 1
    return toks
```

Порядок: если `HEAD.match()` не сработал — вызвать `fields()` для этого отрезка.
Медленный путь включается на 0,001 % записей и на скорость не влияет: на проверенном
срезе 590 794 записи разобраны за 3,3 с, из них медленным путём 10.

## Грабли

| Симптом | Причина | Решение |
|---|---|---|
| Совпадает 0 % записей | поля разделены переводами строк | `\s*` после каждой запятой |
| Совпадает ~6 % записей | номер транзакции в **hex** | `[0-9a-f]+` вместо `\d+` |
| Разбор возвращает 2 поля вместо 19 | запятые ищутся на глубине 0 | разделитель — запятая на глубине **1** |
| Ложные границы записей | строки стека начинаются с `{` | якорь `\n{` + 14 цифр + `,` |
| `SyntaxError: bytes can only contain ASCII` | кириллица внутри `rb"…"` | в байтовых регулярках только ASCII |
| Пропадает первая запись при старте с её смещения | `off` указывает на `{`, а якорь ищет `\n{` | если данные начинаются с `{` + 14 цифр + `,`, дописать `\n` и уменьшить абсолютное смещение на 1 |
| Пропадает запись на стыке блоков | блок кончился внутри записи | переносить хвост от последнего маркера |
| Ложные «потери» в `--check` при мелком `--chunk` | перекрытие 15 байт на маркер в 17 байт | перекрытие 16 байт, хвост копить по потоку, условие по концу матча |
| Текст ошибки у «сложных» записей отличается | в медленном пути остались внешние кавычки, `""` не раскрыт | снимать кавычки поля и раскрывать `""` в обоих путях |

## Проверка полноты

Счётчик «маркеров против разобранных» внутри одного прохода **тавтологичен**: если маркеры
считать по тем же позициям, что и разбор, они совпадут всегда. Нужен независимый пересчёт.

Корректный вариант — считать маркеры по сырому потоку **с перекрытием** в 16 байт: маркер
вместе с запятой — это `\n{` + 14 цифр + `,`, то есть **17 байт**, и он может разрезаться
границей чтения. Хвост нужно накапливать по потоку: `(tail + chunk)[-16:]`, а не `chunk[-16:]`
(иначе при `--chunk` меньше 16 байт перекрытия не останется вовсе).

```python
tail = b""
...
for m in REC.finditer(tail + chunk):
    if m.end() > len(tail):             # маркер дочитался в этом блоке
        n_control += 1
tail = (tail + chunk)[-16:]
```

Условие именно по **концу** маркера. Если писать `m.start() >= len(tail)`, отбрасываются
как раз те маркеры, которые начались в хвосте и дочитались в новом блоке, — перекрытие
перестаёт помогать и пересчёт остаётся заниженным (проверено: на 4 МиБ блоками по 64 КиБ
такой вариант даёт 37 152 вместо 37 162).

Без перекрытия пересчёт **занижен**: на 21,5 ГБ с блоками по 64 МиБ это около 47 записей —
то есть реальная потеря в десятки записей утонет в шуме счётчика. С перекрытием в 16 байт
и условием по концу матча пересчёт точен при любом размере блока: проверено 18.11.2026 на
4 МиБ (`--chunk 61` и `--chunk 4096`: 37 162 = 37 162) и на 256 КиБ (`--chunk 1`:
2 283 = 2 283). На срезе 4 МиБ разобрано 37 161 — последняя запись начинается до границы
чтения и не дочитана, её маркер считается, но строка не пишется.

`parse_lgp.py --check` включает такой пересчёт; стоит примерно +9 % времени
(замер на 1 ГиБ: 52,4 с без него, 57,1 с ним; на срезе 64 МиБ 18.11.2026: 3,4 с и 3,6 с —
+6 %). При расхождении счётчиков скрипт пишет предупреждение в stderr.

Про 2 284 и 2 625: в первом прогоне расхождение с маркерами составляло 2 625 записей;
после включения второго уровня медленным путём разобрано **2 284**. Остаток приходился
на книгу переноса между блоками (перенесённая запись считалась дважды), а не на потерю данных.

## Что делает парсер с полями

- Медленный путь принимает записи с **17 полями и больше** — 18-е и 19-е поля для разбора
  не нужны. Требование «≥ 19» отбрасывало бы записи журналов с другим числом полей.
- Кавычки-экранирование `""` в поле «Комментарий» раскрывается в `"` в обоих путях,
  а внешние кавычки поля снимаются: текст ошибки одинаков независимо от того, каким путём
  разобрана запись. Иначе `GROUP BY comment` в [`analysis.md`](analysis.md) даёт две группы
  для одного текста.
- Смещение `off` пишется в выгрузку вместе с `src` (имя файла): у журнала из нескольких
  `.lgp` одинаковые `off` встречаются в разных файлах.

## Эталонная реализация

[`parse_lgp.py`](parse_lgp.py): два уровня разбора, чтение блоками, независимый счётчик,
проверка входного файла (не журнал → код возврата 2), восстановление разделителя при старте
ровно по `off`, выгрузка CSV (UTF-8 с BOM, `;`) / TSV (для [`load_sqlite.py`](load_sqlite.py)).
