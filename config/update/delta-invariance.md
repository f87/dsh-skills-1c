# Инвариант дельты: перечень доработок не меняется от обновления

**Правило.** После обновления расхождения между целевой конфигурацией и конфигурацией поставщика
(поставщиков) должны быть **такими же, как до обновления**. Перечень доработок не меняется от обновления.

**Цель:** не потерять доработки и не увеличить степень расхождения (модифицированности) новой
конфигурации относительно конфигурации поставщика (или поставщиков, если их несколько).

Проверка обязательна для каждой сборки — наравне с типами и загрузкой
([`acceptance.md`](acceptance.md)); если поставщиков несколько, перед ней проверяется состав поставок —
[`deliveries-invariance.md`](deliveries-invariance.md).

---

## 1. Определения

| Термин | Значение |
|---|---|
| **Δ (дельта)** | множество объектов метаданных, файлы которых отличаются от версии поставки, плюс собственные объекты (которых в поставке нет) |
| **Доработка** | элемент Δ |
| **Степень расхождения** | состав Δ и объём отличий внутри каждого объекта |
| **Δ_before / Δ_after** | дельта до и после обновления |

Δ считается **по содержимому файлов** (SHA1), а не по уровню поддержки и не по `configVersion`
(`config/xml-format.md`). Уровень поддержки — отдельная ось: объект может быть снят с поддержки,
но не изменён (см. §5.2).

---

## 2. Инвариант

```
Δ_after = Δ_before
```

Допустимые отклонения — только два:

1. **Объект удалён поставщиком** → он удаляется из результата и попадает в отчёт для пользователя (§5.1).
2. **Объект не был доработан, но был снят с поддержки** → при обновлении ставится на поддержку
   (уровень 0), состав Δ не меняется (§5.2).

Нарушения:

| Категория | Что значит | Последствие |
|---|---|---|
| `lost` | был доработан → стал совпадать с поставкой | **потеря доработки** (функциональность пропала) |
| `new` | не был доработан → стал доработанным | **рост расхождения** (следующее обновление дороже) |
| `ownAdded` / `ownRemoved` | изменился состав собственных объектов | изменение состава конфигурации без решения человека |

Оба класса (`lost`, `new`) **не видны** при загрузке в пустую базу: «загрузилось» ≠ «доработки на месте».

---

## 3. Проверка

### 3.1. Инструмент

```powershell
node config\update\delta-check.js <beforeTree> <afterTree> <vendorTree> [<vendorTree2> ...] [--json out.json]
```

- `beforeTree` — состояние **до** обновления (предыдущий результат или текущая конфигурация);
- `afterTree` — собранный результат;
- `vendorTree` — одна или несколько выгрузок поставщиков. При нескольких поставщиках передайте все:
  объект считается неизменённым, если совпадает с версией **любого** из них.
  Сами поставки лежат в `Ext\ParentConfigurations\*.cf` рабочего дерева — их нужно предварительно
  выгрузить в XML: [`config/vendor-configs.md`](../vendor-configs.md).

Коды возврата: `0` — инвариант соблюдён; `1` — есть `lost`/`new`/`own*`; `2` — есть `removed`
(допустимо, но требует записи в отчёте).

### 3.2. Сверка с уровнями поддержки

```powershell
pwsh -File config\support-state.ps1 -Tree <afterTree>
```

- объекты уровня `1`/`2` — ровно те, что в Δ_after (изменённые);
- объекты уровня `0` — вне Δ_after (не изменённые);
- объект вне Δ с уровнем `1`/`2` — кандидат на постановку на поддержку (§5.2).

### 3.3. Порядок в конвейере

1. `beforeTree` — дерево, с которым сравниваем (обычно `current` или предыдущий `result_*`).
2. Собрали `afterTree` (каркас → типы → элементы → модули).
3. `delta-check.js` до загрузки в базу — дешёвая проверка, ловит потерю/рост до 40-минутной загрузки.
4. После загрузки — `CheckModules -ThinClient -Server` (`config/checkmodules.md`) и остальная приёмка.
5. `removed`-объекты и `lost`/`new` (если остались) — в отчёт с решением.

---

## 4. Отчёт

Для каждого отклонения — строка в отчёте сборки (`other/reports-handover.md`):

```markdown
| Объект | Категория | Что было | Что стало | Решение |
|---|---|---|---|---|
| Document.Заказ | lost | доработан (2 реквизита, правка модуля) | совпадает с поставкой | восстановлено из current |
| Catalog.Старый | removed | доработан, снят с поддержки | удалён поставщиком | удалён, данные не переносятся |
| Catalog.Банки | new | не доработан | отличается на 1 файл | артефакт слияния, файл возвращён поставке |
```

Отчёт обязателен: он — доказательство, что доработки не потеряны, а удаления осознаны.

## 5. Особые случаи

### 5.1. Объект удалён поставщиком

Объект был в `beforeTree` (возможно, доработан и снят с поддержки), в новой поставке его нет.

1. Объект **удаляется** из результата (восстанавливать «для совместимости» нельзя — даёт несоответствия
   предопределённых данных, см. `other/known-limitations.md`).
2. В отчёт — строка: что это была за доработка, что объект удалён поставщиком, что данные по нему
   не переносятся / будут удалены реорганизацией.
3. Ссылки на объект чистятся (`prunerefs.js`, `prunetypes.js`), а не «подпираются» заглушкой.

`delta-check.js` показывает это как `removed` (код возврата `2`).

### 5.2. Объект не доработан, но снят с поддержки

Бывает: объект когда-то сняли с поддержки «на всякий случай», файлы при этом не менялись. После
обновления такой объект должен **вернуться на поддержку** — изменений нет, держать его снятым значит
без причины увеличивать расхождение.

```powershell
pwsh -File config\support-state.ps1 -Tree <afterTree> -ObjectName '<Объект>' -Level 0
```

Условие: файлы объекта побайтно равны поставке — это и есть определение «не доработан»
(`config/support-state.md`, §4.4). При нескольких поставщиках уровень ставится в записи той поставки,
которой принадлежит `uuid`.

### 5.3. Переименование поставщиком

Поставщик переименовал объект/реквизит, сохранив `uuid` (`X` → `УдалитьX` или наоборот). Это **не**
потеря и **не** рост расхождения: объект тот же, меняется имя. Действие — переименовать ссылки
(`renames-refs.md`), а не восстанавливать старый объект.
`delta-check.js` опирается на имена из `ConfigDumpInfo`, поэтому переименование может выглядеть как
`removed` + `new`; в отчёте укажите пару «старое имя → новое имя» и `uuid`.

### 5.4. Несколько поставщиков

Если конфигурация стоит на поддержке нескольких поставок (например, основная + модуль), передавайте
`delta-check.js` все деревья поставок. Объект, совпадающий с любой из поставок, считается неизменённым;
объект, которого нет ни в одной, — собственный.

## 6. Критерии приёмки

| # | Проверка | Ожидание |
|---|---|---|
| 1 | `delta-check.js` | `lost = 0` и `new = 0` |
| 2 | `delta-check.js` | `ownAdded = 0`, `ownRemoved = 0` (или каждое обосновано в отчёте) |
| 3 | `delta-check.js` | `removed` — каждый объект в отчёте с причиной и решением |
| 4 | `support-state.ps1` | уровень `1`/`2` только у объектов из Δ_after; «снят, но не изменён» — поставлен на поддержку |
| 5 | Повторный прогон | `delta-check.js` на `afterTree` против самого себя даёт `ok`, `preserved = |Δ_after|` |

Если `lost` или `new` не нулевые — сборка **не сдаётся**: чинится слияние, а не отчёт.

## 7. Проверено (инструмент)

Демо-набор `DEMO_SSL` (одна конфигурация, 6 состояний; поставка — «0. На замке»):

| Сценарий | Результат `delta-check.js` | Код |
|---|---|---|
| `2 → 2` (ничего не меняли) | `preserved = 1`, нарушений нет | 0 |
| `2 → 0` (доработку откатили) | `lost = 1` (`Document._ДемоНачислениеЗарплаты`) | 1 |
| `2 → 3` (добавили правку регистра) | `new = 1` (`InformationRegister._ДемоГрафикиРаботы`) | 1 |
| `5 → 5` | `preserved = 3`, свои объекты на месте | 0 |
| `5 → 2` (потеряли две доработки и свои объекты) | `lost = 2`, `ownRemoved = 2` | 1 |
| `2 → 2` без объекта (удалён) | `removed = 1` (`Document._ДемоНачислениеЗарплаты`) | 2 |

Время на дереве ~12,7 тыс. файлов — секунды; на крупной конфигурации — минуты (хэширование файлов).
