# Инвариант поставок: ни один поставщик не теряется

Правило обновления для конфигурации, которая стоит на поддержке **нескольких** поставщиков
(продукт + отраслевое дополнение и т. п.). Универсально для любой 1С 8.3.
Проверено 28.10.2026 на 8.3.27.1859 (п.3 — прямой эксперимент, см. ниже).

## 1. Правило

> Сколько поставок было до обновления — столько должно остаться после. Менять можно только **порядок**
> поставок (по правилам главной поставки) — но не состав.

Проверку делаем **дважды**: на входе (что грузим) и на выходе (что вернула 1С). Молчаливая потеря
поставки не видна ни в логе загрузки, ни в `CheckModules`, ни в `.cf` — только в `.bin`.

## 2. Почему это опасно

Поставка в `Ext\ParentConfigurations.bin` — это то, что делает объекты «типовыми»: их уровень `0`
означает «не редактировался, поддержан поставщиком» ([`../support-state.md`](../support-state.md)).
Если запись поставки пропала, её объекты перестают считаться поставкой:

- сравнение с поставкой ломается: `delta-check.js` начнёт видеть «свои» объекты там, где их нет,
  а `support-state.ps1 -Compare` — расхождение по всем объектам дополнения;
- вернуть объекты в поставку можно только из резервной копии `.bin` — «Поддержка → Обновить» уже
  не подхватит: обновлять нечего;
- ошибка не всплывает на загрузке: конфигурация компилируется и работает, меняется только поддержка.

## 3. Как теряется (проверено)

**Дерево с одноставочным `.bin` затирает вторую поставку.** Загрузка `LoadConfigFromFiles` заменяет
`Ext\ParentConfigurations.bin` целиком тем, что лежит в дереве; 1С не сверяет его с базой и не
дополняет отсутствующие поставки.

Эксперимент (8.3.27.1859, 28.10.2026):

| Шаг | Что делали | Результат |
|---|---|---|
| 1 | дерево с `.bin` из **2** поставок (вторая — искусственная, для теста) загрузили в чистую базу | exit 0, **0 сообщений**; `.bin` после выгрузки байт-в-байт равен загруженному (`bin_diff` — «структурно идентично») |
| 2 | в это же дерево положили исходный `.bin` с **1** поставкой и загрузили **в ту же базу** | exit 0, только штатные «Возможно неверная ссылка … внутри справки»; **ни одного сообщения о потере поставки** |
| 3 | выгрузили конфигурацию и посмотрели `.bin` | `count = 1`; SHA1 совпал с одноставочным исходником (`B81AF2D9…`) — вторая поставка исчезла, её записи объектов тоже |

Второй вывод из шага 1: 1С **не проверяет** ни порядок поставок, ни `parentGuid`, ни соответствие
загружаемого `.bin` тому, что уже стоит в базе, — принимает то, что дали (совпадает с [`../supply/deliveries.md`](../supply/deliveries.md) §3).
Значит ответственность за состав поставок — на сборке, и проверять его нужно самим.

## 4. Откуда берётся одноставочное дерево

| Источник | Что в нём |
|---|---|
| выгрузка новой версии **продукта** от вендора | только поставка продукта — дополнения там нет |
| результат обновления через `.cfu` одной поставки | гипотеза: обновляется только «своя» поставка, вторая в `.bin` остаётся; не проверялось ([`../known-limitations.md`](../../other/known-limitations.md) п.10) |
| дерево, собранное заново из «чистой» поставки (`skel.js` и подобные) | одна поставка, если не перенести `.bin` из текущей конфигурации |
| ручная правка `.bin` или его пересборка «с нуля» | сколько блоков записали, столько и останется |

**Правило сборки:** в результирующем дереве `Ext\ParentConfigurations.bin` должен содержать **все**
поставки конфигурации-источника; при пересборке — [`../supply/build-and-check.md`](../supply/build-and-check.md)
(`--main`/`--extra`), копии `*.cf` — [`../vendor-configs.md`](../vendor-configs.md).

## 5. Гейты

### 5.1 До загрузки (вход)

```powershell
node config\supply\bin_summary.js <tree>\Ext\ParentConfigurations.bin
```

Сверяем: `count` и пары `name` + `version` поставок — с эталоном «до обновления». Состав должен
совпасть, порядок — по правилам главной поставки ([`../supply/which-is-main.md`](../supply/which-is-main.md)).
Копии `*.cf`: их ровно столько, сколько поставок с `flag=0`, SHA1 копий = SHA1 вендорских файлов
([`../vendor-configs.md`](../vendor-configs.md) §2).

**Состав берётся из исходной конфигурации, а не из задания на сборку.** Если в рабочей базе или эталоне
две поставки, а в собранном дереве одна — это дефект сборки, даже когда инструкция проекта требует
одну: 1С принимает обе ([`../supply/deliveries.md`](../supply/deliveries.md)), а дерево с одной поставкой
молча выключает дополнение из поддержки (R20).

### 5.2 После загрузки (выход)

```powershell
node config\supply\bin_summary.js <dump>\Ext\ParentConfigurations.bin
node config\supply\bin_diff.js <before.bin> <dump>\Ext\ParentConfigurations.bin
```

`bin_diff` показывает разницу в числе поставок отдельной строкой («число поставок N != M») и поставку,
которая есть только с одной стороны; отличия в уровнях и записях он печатает по каждой поставке.
Состав и порядок после обновления должны совпадать с эталоном; допустимы только изменения уровней,
которые вы запланировали.

При пересборке `.bin` уровни **пересчитываются** по правилу 0/1
([`../supply/support-levels.md`](../supply/support-levels.md)), а не копируются из базы заказчика:
копирование статусов разносит `2` на дочерние записи и выключает объект из автоматического обновления
поставщика. При нескольких поставках — `support-levels-multi.js`: состав поставок при этом не меняется,
меняются только уровни, и каждая запись сравнивается со своей поставкой (уровень главной не переносится).

### 5.3 Приёмка `.cf`

[`accept_cf.ps1`](../supply/build-and-check.md) с `-ExpectedBin <эталон.bin>`: сверяет `.bin` полученной
конфигурации по SHA1 и перечисляет копии `*.cf` — то же, что п.5.2, но на готовом артефакте.

## 6. Что делать, если поставка потеряна

1. Взять `.bin` из резервной копии «до» (или из текущей рабочей базы) — там все поставки.
2. Положить его в дерево и загрузить дерево снова (или пересобрать двухпоставочный `.bin` из
   сохранённых одноставочных: `build_two_deliveries_bin.js --main <продукт> --extra <дополнение> --flag 0`).
3. Проверить `count`, пары `name`+`version` и копии `*.cf` (п.5).
4. Пересчитать дельту: `delta-check.js` — после восстановления «своих» объектов станет меньше, категории
   `lost`/`ownRemoved` изменятся. Это ожидаемо, но должно быть объяснено в отчёте.

Восстанавливать поставку «вручную по объектам» (дописывать записи в `.bin`) не нужно и опасно:
список объектов поставки и её `guid`/`parentGuid` берутся из вендорского файла, а не сочиняются.

## 7. В отчёт

Таблица поставок «до» и «после»: `name`, `version`, `vendor`, `flag`, число записей, распределение
уровней `0/1/2`, порядок. Плюс SHA1 файла `.bin` и перечень копий `*.cf` с SHA1
([`../reports-handover.md`](../../other/reports-handover.md)).
