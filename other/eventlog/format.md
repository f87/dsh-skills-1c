# Формат файлов журнала регистрации

Когда применять: нужно разобрать `.lgp`/`.lgf` без платформы, понять поле записи
или расшифровать числовые коды.

Проверено на журнале платформы 8.3 (формат `1CV8LOG(ver 2.0)`; точный билд в файле
не хранится), ноябрь 2026: `.lgp` 21,5 ГБ, 198,3 млн записей; `.lgf` 314 КБ, 3 810 записей.

## Файлы в каталоге `1Cv8Log`

| Файл | Что внутри |
|---|---|
| `<YYYYMMDDhhmmss>.lgp` | **данные**: сами события |
| `1Cv8.lgf` (или `<имя>.lgf`) | **описания**: справочники пользователей, компьютеров, приложений, событий, метаданных, серверов, портов |
| `.lgd`, `.lgx` | гипотеза: служебные файлы индексации и разметки, для разбора не используются; в проверенном каталоге их роль не устанавливалась |

Имя `<YYYYMMDDhhmmss>.lgp` — момент начала файла. Один файл может покрывать месяц
и десятки гигабайт, если ротация настроена по размеру.

## Устройство файла

И данные, и описания начинаются одинаково:

```
1CV8LOG(ver 2.0)                              ← маркер формата
<GUID>                                        ← GUID журнала, одинаковый в .lgp и .lgf
                                              ← пустая строка
```

**Пустая строка есть в обоих типах файлов**, поэтому по ней файл данных не отличить.
Различайте по первой записи после пустой строки:

- `.lgp` → `{` + 14 цифр + `,` (дата события);
- `.lgf` → `{` + код массива + `,` (например `{4,"_$Session$_.Start",1}`).

Дополнительный признак: GUID в `.lgf` и `.lgp` одного каталога совпадают.

Ещё отличие: записи `.lgp` разделены `\r\n`, а записи `.lgf` — `,\r\n`, то есть в файле
описаний они идут по одной в строке, но через запятую. Поэтому `.lgf` режут по балансу
скобок, а не по границе строки ([`parse_lgf.py`](parse_lgf.py)).

- Кодировка: **UTF-8 с BOM**.
- Переводы строк: **CRLF**.

## Запись: 19 полей верхнего уровня

```
{20261009093000,C,
{24569f5bb5980,16beaa9bd},10,6,2,12521162,4,I,"",0,
{"U"},"",3,9,0,123456,0,
{2,1,1,2,1}
}
```

| № | Поле | Значение |
|---|---|---|
| 1 | Дата/время | `yyyyMMddHHmmss` |
| 2 | Статус транзакции | `N` нет, `U` не завершена, `R` отменена, `C` зафиксирована |
| 3 | Транзакция | `{время×10000, номер}` — **оба в hex** |
| 4 | Пользователь | индекс в массиве `.lgf` |
| 5 | Компьютер | индекс |
| 6 | Приложение | индекс |
| 7 | Соединение | номер соединения |
| 8 | **Событие** | индекс |
| 9 | Важность | `I` информация, `E` ошибка, `W` предупреждение, `N` примечание |
| 10 | Комментарий | текст в кавычках, экранирование `""`, **внутри бывают переводы строк** |
| 11 | Метаданные | индекс, `0` = не заполнено |
| 12 | Данные | вложенная структура, см. ниже |
| 13 | Представление данных | строка в кавычках |
| 14 | Сервер | индекс в массиве серверов |
| 15 | Основной порт | **индекс**, не значение |
| 16 | Вспомогательный порт | индекс |
| 17 | **Сеанс** | номер сеанса |
| 18 | Кол-во доп. метаданных | в проверенном журнале всегда `0` |
| 19 | Разделители данных | в проверенном журнале константа `{2,1,1,2,1}` |

Число полей зависит от версии платформы и настроек разделения данных: 18-е поле задаёт
количество дополнительных метаданных и определяет фактическую длину записи.
Ориентируйтесь на «полей ≥ 17», а не ровно на 19: парсер принимает и 17-полевые записи —
18-е и 19-е поля для разбора не нужны (проверено 18.11.2026 на синтетической записи
с вложенностью 5 уровней).

## Поле 12 «Данные»

| Вид | Смысл |
|---|---|
| `{"U"}` | Неопределено |
| `{"S","строка"}` | Строка |
| `{"N",123}` | Число |
| `{"B",0}` / `{"B",1}` | Булево |
| `{"D",20261022084052}` | Дата |
| `{"R",<код>:<guid>}` | Ссылка на объект |
| `{"P",{...}}` | Структура/массив; **вложенность бывает 5 и более уровней** |
| `{"O",{"#",<guid>,<guid>}}` | Ссылка объекта |

Длинные значения встречаются: в проверенном журнале поле «Данные» достигало тысяч символов
(XML-структура пользователя). Это важно при выборе типа столбца в СУБД —
см. [`sqlite.md`](sqlite.md).

## Поле 3 «Транзакция»

```
{2456b7d521590,2b5299307}
```

- первая часть — секунды с 01.01.0001 × 10000, в hex (`0x2456b7d521590` → 2026-10-16 23:59:37);
- вторая — номер транзакции, в hex.

В интерфейсе 1С показывается `(<знаковое 32-битное>)`, то есть **младшие 32 бита** второй части:

```
0x2b5299307 & 0xFFFFFFFF = 0xB5299307 = -1255566585
```

Без отбрасывания старших бит получаются числа вида `7334368007`.
Для поиска по номеру из интерфейса храните отдельное поле — младшие 32 бита со знаком.

Пара `_$Transaction$_.Begin` / `_$Transaction$_.Commit` имеет **одинаковый** идентификатор.
Связывать «начало» и «фиксацию» надёжно по **паре** `(время, номер)`: у `Begin` и `Commit`
одной транзакции совпадают обе части (проверено 18.11.2026 на срезе 8 МиБ: 29 740 из
29 751 `Begin` нашли свой `Commit`). Номер в проверенном журнале был уникален
(29 740 из 29 740), но это счётчик сервера, а не гарантия формата: **гипотеза** — при
нескольких серверах кластера номер может повториться. Проверить: журнал, в котором
в массиве `servers` два и более серверов, и поиск одного номера в разных `servers`.

**Статус транзакции — итоговый**: у записи `Begin` тоже стоит `C` (в проверенном срезе —
29 736 из 29 751; у отменённых транзакций там `R` — 10, у незавершённых `U` — 5).
Различать события можно только по коду события, а не по статусу.

## Файл описаний `.lgf`

Записи:

```
{4,"_$Transaction$_.Begin",4}                          код, значение, номер
{1,<guid>,"ИвановИИ",1}                                код, GUID, значение, номер
{5,<guid>,"Справочник.ВерсииРасширений",1}
```

| Код | Массив |
|---|---|
| 1 | пользователи |
| 2 | компьютеры |
| 3 | приложения |
| 4 | события |
| 5 | метаданные |
| 6 | серверы |
| 7 | основные порты |
| 8 | вспомогательные порты |
| 9 | области данных |
| 10–13 | служебное (разделение данных), для отчётов не нужно |

**В записи журнала хранятся индексы, а не значения.** Пример: основной порт `1` в записи
означает значение с индексом `1` из массива `ports_main` (в проверенном журнале — `<значение>`,
порт информационной базы), сервер `1` — имя из массива `servers`. В другом журнале
нумерация будет своей.

Типовые имена событий платформы (коды — свои в каждом `.lgf`):

| Имя | По-русски |
|---|---|
| `_$Session$_.Start` / `.Finish` | Сеанс. Начало / Завершение |
| `_$Transaction$_.Begin` / `.Commit` / `.Rollback` | Транзакция. Начало / Фиксация / Отмена |
| `_$Data$_.Update` / `.Delete` / `.Post` | Данные. Изменение / Удаление / Проведение |
| `_$Job$_.Start` / `.Finish` / `.Error` | Фоновое задание. Запуск / Завершение / Ошибка |
| `_$Session$_.DataZoneChange` | Сеанс. Изменение текущей области |
| `_$User$_.Update` | Пользователи. Изменение |

## Где лежит журнал

- Клиент-серверный вариант: каталог `1Cv8Log` внутри `srvinfo` **каталога установки
  сервера 1С** (например `<Program Files>\1cv8\srvinfo\reg_<порт>\1Cv8Log`), а не рядом
  с файловой базой. `<порт>` — порт кластера (обычно `1541`), а не рабочий порт
  информационной базы из журнала (значения из массива `ports_main`).
- Файловый вариант: каталог базы `1Cv8Log`.
- Выгрузка из интерфейса («Журнал регистрации → Выгрузить в файл…») даёт текст в том же
  формате, но подчиняется фильтрам формы — см. [`analysis.md`](analysis.md).

## Проверка

Что должно сойтись на любом журнале этого формата:

```bash
python parse_lgp.py --input <файл.lgp> --limit 67108864 --check
python parse_lgf.py --input <файл.lgf>
python read_record.py --input <файл.lgp> --offset <off>
```

- `--check` печатает «учтено» и «контроль» — числа должны совпасть, «не разобрано» = 0;
- `.lgf` даёт ненулевые `users` и `events`, а не «файл данных»;
- `read_record.py` по `off` печатает запись, начинающуюся с `{` + 14 цифр даты;
- у записей среза ровно 19 полей (18-е = `0`, 19-е = `{2,1,1,2,1}`) — проверяется
  выгрузкой одной записи и просмотром глазами.
