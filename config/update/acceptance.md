# Приёмка результата обновления

Конфигурация считается готовой, только если выполнены **все** пункты и подтверждены логами.

| # | Проверка | Команда | Ожидание |
|---|---|---|---|
| 1 | Загрузка дерева в **пустую** базу | `DESIGNER /F<ib> /LoadConfigFromFiles"<tree>" /Out<лог>` | EXIT 0; в логе нет `Файл объекта не существует`, `Неверный путь`, `Неизвестный объект`, `Неизвестное имя типа`, `Недопустимый тип`, `не является регистратором`, `не соответствует`, `Дублирование имени`, `InternalInfo` |
| 2 | Синтаксис | `/CheckModules -ThinClient -Server` (`config/checkmodules.md`) | EXIT 0, «Синтаксических ошибок не обнаружено!»; одиночный `-ThinClient` **не проверяет серверные модули** |
| 3 | **Определяемые типы** | `node config\update\mergetypes.js <tree> <currentTree> <report.json>` (без `--apply`) | `addedFromCurrent = 0`; `missing` пуст или объяснён |
| 4 | Сверка с базой (для непустой БД) | Конфигуратор → «Сравнить конфигурацию» с базой пользователя | по определяемым типам нет строк `<--` |
| 5 | Выгрузка | `/DumpCfg"<CF>"` | EXIT 0; размер соответствует вашей конфигурации (пример: ~1,5 ГБ) |
| 6 | Целостность `.cf` | `CREATEINFOBASE` + `/LoadCfg <CF>` в чистую базу | EXIT 0, «Загрузка конфигурации успешно завершена» |
| 7 | Артефакт | размер + MD5 | зафиксировать в отчёте |
| 8 | **Инвариант дельты** | `node config\update\delta-check.js <beforeTree> <afterTree> <vendorTree…>` (`delta-invariance.md`) | `lost = 0`, `new = 0`, `ownAdded/ownRemoved = 0`; `removed` — каждый объект в отчёте |
| 9 | Отчёты | — | итоговый отчёт, журнал сборки, список битых ссылок, состояние ролей, отклонения дельты |

## Если правили саму выгрузку (XML/поддержку)

Дополнительно к таблице — для задач «снять/поставить на поддержку», «откатить объект к поставке»,
«добавить реквизит/объект».

| # | Проверка | Ожидание |
|---|---|---|
| 10 | Обратная выгрузка после `LoadConfigFromFiles` | `Ext\ParentConfigurations.bin` **побайтно равен** записанному (1С сохраняет выставленные уровни) |
| 11 | Сверка деревьев без `ConfigDumpInfo.xml` | 0 отличий; `ConfigDumpInfo.xml` отличается **только** `configVersion` |
| 12 | Объекты, возвращённые на поддержку | `config/support-state.ps1 -Compare <vendor tree>` → 0 отличий от поставки |
| 13 | MD5 `.cf` | между базами **не сравнивать**: воспроизводим только внутри одной базы |

Подробности и команды — [`config/support-state.md`](../support-state.md),

## Если поставщиков несколько

Правило — [`deliveries-invariance.md`](deliveries-invariance.md): сколько поставок было, столько осталось;
менять можно только порядок ([`../supply/which-is-main.md`](../supply/which-is-main.md)).

Таблица ниже обязательна всегда, когда в исходной конфигурации или рабочей базе больше одной поставки —
**независимо от того, что написано в задании или инструкции сборки**. Требование «собрать с одной
поставкой» не отменяет гейты: сначала правят инструкцию (R21), потом собирают.

| # | Проверка | Ожидание |
|---|---|---|
| 14 | Состав поставок в дереве **до** загрузки: `node config\supply\bin_summary.js <tree>\Ext\ParentConfigurations.bin` | `count` и пары `name`+`version` совпадают с эталоном «до обновления» |
| 15 | `.bin` **после** выгрузки: `node config\supply\bin_diff.js <before.bin> <dump>\Ext\ParentConfigurations.bin` | `count` совпадает; «поставка есть только с одной стороны» — 0 |
| 16 | Копии `*.cf` в `Ext\ParentConfigurations\` | по одной на каждую поставку с `flag=0`, SHA1 совпадает с вендорскими ([`../vendor-configs.md`](../vendor-configs.md)) |
| 17 | Уровни поддержки: `node config\supply\support-levels.js ... --json <report>.json`; при нескольких поставках — `node config\supply\support-levels-multi.js ... --map <map>.json` | записей уровня `2` — 0 (или согласованный список исключений); `count`/`objects`/`mode` не изменились; повторный прогон даёт расхождений 0 ([`../supply/support-levels.md`](../supply/support-levels.md)) |
| 18 | Round-trip уровней: `LoadConfigFromFiles` → `DumpConfigToFiles` | SHA1 `.bin` совпадает с записанным; выгрузка отличается от дерева только `ConfigDumpInfo.xml` и `Ext\ParentConfigurations.bin` |
| 19 | Корни и дети в многопоставочном `.bin`: отчёт `support-levels-multi.js --json` | корней `0` с дочерними `1` — 0; записей без имени в `ConfigDumpInfo` — 0 |
| 20 | Идемпотентность и состав на многопоставочном `.bin`: повторный прогон + `bin_diff.js` до/после | изменений 0; состав записей и `mode` не менялись — только уровни |

## Допустимые предупреждения

- «Возможно неверная ссылка `ПутьККартинке` / `v8mnghelp://` внутри справки» — не влияет на загрузку.
- Единичные «Неизвестный объект метаданных» для ссылок модуля на переименованные реквизиты — должны быть
  перечислены в отчёте.

## Чего проверки НЕ дают

- `CheckModules` проверяет синтаксис, но не ссылки в рантайме и не миграцию данных.
- Загрузка **не сообщает о потере поставки**: дерево с `.bin` из одной поставки затирает остальные
  молча, exit 0 и «0 сообщений» ([`deliveries-invariance.md`](deliveries-invariance.md) §3).
- Загрузка `.cf` в пустую базу **не проверяет корректность определяемых типов** (см. п.3–4) и не проверяет
  реструктуризацию базы с данными.
- Полная «Проверка конфигурации» в Конфигураторе (ссылки, формы, права) — отдельный прогон; в проекте
  ERP 2.5.27.98 она не запускалась (использовались загрузка + `CheckModules` + выборочные формы).
- Для проверки обновления с данными **нельзя** использовать поставленный `.dt` (демо-база с данными).

## Фиксация результата

```powershell
$f = Get-Item "<CF>"
"{0}: {1:N1} МБ  MD5 {2}" -f $f.Name,($f.Length/1MB),(Get-FileHash $f.FullName -Algorithm MD5).Hash
```

Занести в итоговый отчёт и журнал сборки (`other/reports-handover.md`).
