# Журнал регистрации 1С: формат, разбор, загрузка, анализ

Когда применять: есть файлы `.lgp`/`.lgf` из `1Cv8Log` (клиент-серверный или файловый вариант),
нужно разобрать их без платформы, перегнать в СУБД для быстрых запросов или понять, что
в журнале происходит и кто создаёт объём.

Проверено на журнале платформы 8.3 (формат `1CV8LOG(ver 2.0)`; точный билд в файле не хранится),
ноябрь 2026: `.lgp` 21,5 ГБ, 198,3 млн записей, около 500 тыс. сеансов; `.lgf` 314 КБ,
3 810 записей. Подходит любой журнал этого формата — коды событий и приложений свои
в каждом журнале, поэтому в рецептах они не зашиты.

## Инструменты

| Скрипт | Назначение |
|---|---|
| [`parse_lgp.py`](parse_lgp.py) | парсер `.lgp`: `--input`, `--from`, `--limit`, `--chunk`, `--out`, `--format csv\|tsv`, `--check` |
| [`parse_lgf.py`](parse_lgf.py) | справочник `.lgf` → JSON, SQL (`--sql`) или сразу в базу (`--sqlite`) |
| [`read_record.py`](read_record.py) | запись целиком по `off` из базы (файл — из поля `src`) |
| [`load_sqlite.py`](load_sqlite.py) | загрузка выгрузки в SQLite: таблица → данные → индексы → сверка |

Все пути — аргументами, настроек проекта внутри нет.
**Зависимостей нет вообще** — только стандартная библиотека Python 3 (`sqlite3` входит в неё).
Сервер СУБД не нужен: база — один файл.
Скрипты написаны на Python 3 и автономны: скилл не требует Node, Java или установленных пакетов,
поэтому его можно класть в хранилище с любым языком инструментов.

## Быстрый старт

```bash
# 1. что вообще в файле (последняя запись среза может не дочитаться —
#    она начинается до границы --limit и кончается после)
python parse_lgp.py --input 20260101000000.lgp --limit 67108864

# 2. справочники кодов: JSON для скриптов, SQL для базы
python parse_lgf.py --input 1Cv8.lgf --out lgf.json
python parse_lgf.py --input 1Cv8.lgf --sql dict.sql

# 3. выгрузка: tsv — для базы (csv — открыть в Excel: UTF-8 с BOM, ';')
python parse_lgp.py --input 20260101000000.lgp --out events.tsv --format tsv

# 4. база (сервер не нужен, файл на диске)
python load_sqlite.py --tsv events.tsv --db eventlog.sqlite --expect <строк>
python parse_lgf.py --input 1Cv8.lgf --sqlite eventlog.sqlite

# 5. запросы — любым клиентом SQLite или из Python
python -c "import sqlite3; print(sqlite3.connect('eventlog.sqlite').execute('SELECT COUNT(*) FROM events').fetchone())"
```

## Минимум, который нужно помнить

1. `.lgp` — **текстовый** формат: маркер `1CV8LOG(ver 2.0)`, GUID, пустая строка, дальше записи
   в фигурных скобках. Бинарного разбора не нужно.
2. Имена пользователей, приложений, событий и метаданных — в отдельном `.lgf`; без него
   в записи остаются только числовые индексы.
3. Пара «Транзакция. Начало + Фиксация» — **две записи на транзакцию**; в промышленных базах
   это до 90 % объёма.
4. Записи многострочные: резать только по границам `\n{` + 14 цифр + `,` с контролем
   кавычек и скобок.
5. Номер транзакции в файле — **hex**, в интерфейсе 1С — младшие 32 бита со знаком.
6. Поле «Данные» бывает вложено на 5+ уровней: простая регулярка теряет такие записи молча.
7. Загружать в базу нужно **сначала данные, потом индексы**; иначе вместо часов — сутки.
8. `off` имеет смысл только вместе с `src` (имя файла): у журнала из нескольких `.lgp`
   смещения повторяются.
9. 20 ГБ журнала — это ≈48 ГиБ файла SQLite и ≈2 часа на полный цикл; сервер СУБД не нужен.

## Что проверено

| Проверка | Результат |
|---|---|
| `parse_lgf.py` на реальном `.lgf` | 176 пользователей, 188 компьютеров, 13 приложений, 355 событий, 1 685 метаданных, 3 сервера, 31 + 16 портов, 2 области |
| `parse_lgp.py` | 1 ГиБ = 9 306 617 записей, 0 неразобранных, 17–19 МиБ/с без выгрузки (9,2 МиБ/с с записью TSV) |
| `parse_lgp.py --check` | независимый пересчёт равен основному **при любом** `--chunk`: 37 162 = 37 162 (4 МиБ, `--chunk 61`), 2 283 = 2 283 (256 КиБ, `--chunk 1`) |
| `parse_lgp.py --from <off>` | старт ровно по `off` записи: 3 из 3 записей (раньше первая терялась) |
| Глубокие «Данные» | 17-полевая и 19-полевая записи разобраны запасным путём, кавычки в комментарии раскрыты |
| Выгрузка | 17 колонок (16 полей + `src`); `data` — целиком, `comment` — до 300 |
| Формат | у всех записей среза ровно 19 полей, 18-е = 0, 19-е = `{2,1,1,2,1}` |
| Транзакция | `0x2456b7d521590` → 2026-10-16 23:59:37; `0x2b5299307` → −1255566585 |
| Сквозной сценарий | 20 из 20 случайных строк: `off` → `read_record.py` совпал по времени; 5 из 5 по `src` + `off` из SQLite |
| SQLite, 1 ГиБ журнала (9 306 617 записей) | разбор в TSV 112 с, загрузка 52 с (177 тыс. строк/с), 12 индексов 82 с, база 2,3 ГиБ; все рецепты `analysis.md` выполняются |
| 21,5 ГБ журнала (198,3 млн записей) | база SQLite 48 ГиБ; оценка полного цикла по замерам — ≈2 ч (разбор ≈40 мин, загрузка ≈18 мин, индексы 30–70 мин) |

**Не проверено:** полный цикл `parse_lgp.py` → `load_sqlite.py` на всех 21,5 ГБ не прогонялся —
цифры для этого объёма получены линейной экстраполяцией с 1 ГиБ, а размер базы (48 ГиБ)
подтверждён готовой базой проекта разбора. Роль файлов `.lgd`/`.lgx` в каталоге журнала
не устанавливалась — в [`format.md`](format.md) это помечено как гипотеза.
