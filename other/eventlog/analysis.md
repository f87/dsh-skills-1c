# Методика анализа журнала

Когда применять: журнал уже разобран и загружен в SQLite ([`sqlite.md`](sqlite.md)),
нужно понять, что в нём происходит и кто создаёт объём.

Проверено на журнале 198,3 млн записей, ноябрь 2026. Запросы — для SQLite
(если переносите в другую СУБД, замените `substr(x, 1, n)` на её функцию).

## Базовая единица

**Одна запись журнала = одно событие = одна строка таблицы.** Все метрики считаются
`COUNT(*)` по разрезу, а не подсчётом строк текста.

Если журнал разбит на несколько `.lgp` (суточная ротация), сначала смотрите на `src`:
`SELECT src, COUNT(*) FROM events GROUP BY src` — так видно, все ли файлы загружены
и в каком из них искать запись по `off`.

## Коды событий и приложений — свои в каждом журнале

Числовые коды событий, приложений и метаданных берутся из `.lgf` и **различаются между
журналами**. В рецептах ниже они не зашиты: либо подставляется код из справочника, либо
join по имени.

```sql
-- какие коды в этом журнале
SELECT code, name FROM dict_event ORDER BY code;
SELECT code, name FROM dict_app   ORDER BY code;
```

Если справочников в базе нет, коды берутся из `parse_lgf.py` → JSON.

## Первые срезы

```sql
SELECT d.name, COUNT(*) n
FROM events e JOIN dict_event d ON d.code = e.ev
GROUP BY e.ev, d.name ORDER BY n DESC LIMIT 20;

SELECT a.name, COUNT(*) n
FROM events e JOIN dict_app a ON a.code = e.app
GROUP BY e.app, a.name ORDER BY n DESC;

SELECT u.name, COUNT(*) n
FROM events e JOIN dict_user u ON u.code = e.usr
GROUP BY e.usr, u.name ORDER BY n DESC LIMIT 20;
```

`GROUP BY` включает имя: SQLite разрешает «голый» столбец, но с именем запрос понятнее
и переносится в другие СУБД без правок.

В промышленных базах картина обычно одна: основную часть занимают
`_$Transaction$_.Begin` и `_$Transaction$_.Commit` от фоновых заданий.

## Связка «сеанс → задание»

У транзакционных событий поля «Метаданные» и «Данные» пустые, поэтому задание по ним
не определить. Работает только цепочка:

```
сеанс → запись «Фоновое задание. Запуск» этого сеанса
      → поле «Данные» (имя задания) и «Метаданные» (объект «РегламентноеЗадание.<имя>»)
      → все события этого сеанса
```

```sql
-- сеанс -> задание (имя из метаданных стабильнее, «Данные» бывают пустыми)
SELECT sess, MIN(meta) AS meta, MIN(data) AS data
FROM events
WHERE ev = (SELECT code FROM dict_event WHERE name = '_$Job$_.Start')
GROUP BY sess;

-- транзакции в разрезе заданий
SELECT sj.data,
       COUNT(DISTINCT t.sess) AS sessions,
       SUM(t.n) AS tx
FROM (SELECT sess, COUNT(*) n FROM events
      WHERE ev = (SELECT code FROM dict_event WHERE name = '_$Transaction$_.Begin')
        AND app = (SELECT code FROM dict_app WHERE name = 'BackgroundJob')
      GROUP BY sess) t
JOIN (SELECT sess, MIN(data) data FROM events
      WHERE ev = (SELECT code FROM dict_event WHERE name = '_$Job$_.Start')
      GROUP BY sess) sj USING (sess)
GROUP BY sj.data
ORDER BY tx DESC;
```

Тонкости:

- у части заданий поле «Данные» пустое (`{"S",""}`) — имя берётся из «Метаданных»
  (`РегламентноеЗадание.<имя>`), иначе задание останется безымянным;
- имя в «Данных» может не совпадать с метаданными: у одного объекта «Общее регламентное
  задание» бывает несколько конкретных заданий;
- в сеансе может быть несколько записей о запуске — берите `MIN()` или решайте явно.

## Где лежит текст ошибки

Поле **«Данные»** описывает объект операции (`{"S","Обмен данными с …"}`), а не сообщение.
Текст ошибки со стеком — это поле 10, **«Комментарий»**; в таблице оно хранится в столбце
`comment` (обрезается до 300 символов, переводы строк заменяются пробелом).

Если нужен полный текст со стеком — поднимайте оригинал по `off`
([`read_record.py`](read_record.py)): в `comment` остаётся только начало.

## Ловушка интерфейса 1С: пустой фильтр «События»

При **пустом** поле «События» форма «Журнал регистрации» показывает набор по умолчанию,
в котором **нет транзакционных событий**. Выглядит так, будто их нет вообще.

| Фильтр | Что покажет |
|---|---|
| «События» пусто | только нетранзакционные события |
| «События» = `Транзакция. Начало` | все транзакции |

Проверено на одном сеансе проверенного журнала: 7 записей без фильтра против 29 775
с фильтром. То же правило действует и для выгрузки «Выгрузить в файл…».

Практический вывод: **любые подсчёты в интерфейсе 1С без явного фильтра по событию
занижены**. Для сверки с базой всегда указывайте событие явно.

## Что не является ошибкой

- **Пары `Begin` + `Commit`.** На каждую транзакцию пишется две записи; это не дублирование.
  Отношение `Commit` к `Begin` чуть меньше единицы за счёт откатов.
- **Пустые метаданные у транзакций.** Событие фиксирует факт транзакции, а не объект.
- **Одинаковые транзакции в одну секунду.** Фоновое задание в цикле открывает и закрывает
  десятки транзакций в секунду — шумный, но нормальный режим.

## Знаменатель для долей

Сеансы, **начатые до периода**, в счёт `Сеанс. Начало` не попадают — если взять их
за знаменатель, доля завышается в разы.

```sql
-- сколько сеансов началось в периоде (заниженный знаменатель)
SELECT COUNT(*) FROM events
WHERE ev = (SELECT code FROM dict_event WHERE name = '_$Session$_.Start');

-- сколько различных сеансов встречается в журнале (правильный знаменатель)
SELECT COUNT(DISTINCT sess) FROM events;
```

Замер на проверенном журнале: 52 885 против 501 036. Пример корректной формулировки:
«2 751 сеанс из 501 036 (0,55 %) дают 82,6 % всех записей».

## Полезные разрезы

```sql
-- распределение по часам и дням
SELECT hour, COUNT(*) FROM events
WHERE ev = (SELECT code FROM dict_event WHERE name = '_$Transaction$_.Begin')
GROUP BY hour ORDER BY hour;

SELECT day, COUNT(*) FROM events GROUP BY day ORDER BY day;

-- ошибки по тексту сообщения (поле «Комментарий», не «Данные»!)
SELECT substr(`comment`, 1, 120) AS msg, COUNT(*) n
FROM events
WHERE sev IN ('E','W') AND `comment` <> ''
GROUP BY msg ORDER BY n DESC LIMIT 20;

-- длительность транзакции: связка по паре (время, номер) внутри своего сеанса
SELECT b.sess, b.tx_time, b.ts AS begin_ts, c.ts AS commit_ts
FROM events b
JOIN events c ON c.tx_time = b.tx_time AND c.tx_num = b.tx_num
             AND c.sess = b.sess
             AND c.ev = (SELECT code FROM dict_event WHERE name = '_$Transaction$_.Commit')
WHERE b.ev = (SELECT code FROM dict_event WHERE name = '_$Transaction$_.Begin')
LIMIT 20;
```

`c.sess = b.sess` — страховка: пара `(время, номер)` в проверенном журнале уникальна,
но уникальность номера между серверами — гипотеза ([`format.md`](format.md)), а лишнее
условие по индексированному `sess` ничего не стоит.

## Про «быстро»

Замер на базе 9,3 млн строк (срез 1 ГиБ, SQLite): топ событий 7,6 с, связка «сеанс → задание»
4,2 с, ошибки по тексту 1,8 с, `COUNT(DISTINCT sess)` 0,01 с (по индексу `sess`).
На 198 млн строк умножьте примерно на 20 — кроме запросов, которые целиком идут по индексу
(`COUNT(DISTINCT sess)`, срез по сеансу, по дню), они остаются секундными.

Что требует полного прохода: `JOIN` с `dict_*` и `GROUP BY` по кодам, `GROUP BY` по
`comment`. На непроиндексированном поле `data` — минуты. Если запрос нужен регулярно,
дешевле завести агрегатную таблицу, чем ждать каждый раз.

## Как проверять гипотезы

1. **Сверка с выгрузкой 1С.** Выгрузите тот же сеанс с явным фильтром по событию и сравните
   поштучно по типам событий. Совпадение по редким событиям (10–20 записей) надёжнее,
   чем по массовым.
2. **Сверка с файлом.** Возьмите `off` из базы и прочитайте оригинал
   ([`read_record.py`](read_record.py)) — поля должны совпасть.
3. **Счётчики.** Число маркеров, посчитанное независимо по сырым блокам, против числа
   разобранных записей ([`parsing.md`](parsing.md)).

## Чего избегать в выводах

- «Задание X генерирует шум» без указания объёма и периода;
- вывода по одному срезу без проверки второго разреза (сеанс против пользователя);
- утверждений о причинах поведения платформы без эксперимента — интерфейс ведёт себя
  неочевидно (см. ловушку с фильтром).
