# БСП: `Predefined.xml` — предопределённые каталогов БСП

Речь о двух каталогах БСП, у которых есть `Ext\Predefined.xml`:

- `Catalogs\ИдентификаторыОбъектовМетаданных\Ext\Predefined.xml` — идентификаторы объектов метаданных;
- `Catalogs\НаборыДополнительныхРеквизитовИСведений\Ext\Predefined.xml` — наборы доп. реквизитов и сведений.

При обновлении с сохранением доработок предопределённые нужно **объединять**, и делать это аккуратно:
`LoadConfigFromFiles` и `CheckModules` ошибки здесь **не видят**.

---

## 1. Формат записи

```xml
<PredefinedData xmlns="http://v8.1c.ru/8.3/xcf/predef" version="2.20">
    <Item id="11f4f8a3-e2c3-4d4f-b7e2-a0bfaa1f0194">
        <Name>РегистрСведенийНастройкиВариантовОтчетов</Name>
        <Code/>
        <Description/>
        <IsFolder>false</IsFolder>
    </Item>
</PredefinedData>
```

- `id` — UUID предопределённого; именно он связывает запись с объектом.
- `Name` для `ИдентификаторыОбъектовМетаданных` **кодирует вид и имя объекта**:
  `ДокументЗаказ` → `Documents\Заказ.xml`, `СправочникБанки` → `Catalogs\Банки.xml`.
- Для `НаборыДополнительныхРеквизитовИСведений` имена — это наши/типовые наборы, связи с объектом нет.

---

## 2. Правила слияния

1. **Сливать по `<Item id>` И по имени.** Поставка главнее: запись с тем же UUID или именем не добавляется.
2. **Не добавлять старое имя, если UUID уже есть в поставке под новым именем.** Иначе в каталоге окажутся
   две записи с одним UUID — повреждение метаданных.
3. **Не добавлять имя, если объекта с таким именем нет в результате** (orphan). Для
   `ИдентификаторыОбъектовМетаданных` это проверяется по имени: вид + объект.
4. **Наши наборы в `НаборыДополнительныхРеквизитовИСведений` добавлять можно** — это не orphan,
   а осознанное расширение; в отчёте они перечисляются.

Слияние по `<Name>` без проверки `id` — типовой дефект: при переименовании поставщиком (`X` → `УдалитьX`
или наоборот) появляется вторая запись с тем же UUID.

---

## 3. Гейт

```powershell
node config\update\SSL\checkpredefined.js <resultTree> <vendorTree> <report.json> [catalogsCsv]
```

Критерии: `lost = 0`, `duplicateIds = 0`, `orphanNames = 0`; добавленные имена (`added`) — объяснены.
Отчёт содержит `catalogs[]` (поставка/результат/добавлено/дубли/orphan) и списки `lost`,
`duplicateIds` (с именами записей), `orphanNames`.

---

## 4. Инструмент слияния

```powershell
node config\update\SSL\regmerge.js <tree> <donorTree> predefined <report.json> [removedJson] [catalogsCsv]
```

- сливает по `id` и имени;
- пропускает записи, чей объект отсутствует в дереве (`predefinedSkippedOrphan` в отчёте);
- пропускает ссылки на удалённые поставщиком объекты (если передан `removedJson`);
- список каталогов по умолчанию — два каталога БСП выше.

Проверено на синтетике: поставка 1 имя, донор 3 записи (существующее / новое / отсутствующий объект)
→ `itemsAdded=1`, `predefinedSkippedByName=1`, `predefinedSkippedOrphan=1`.

---

## 5. Грабли

- **Слияние по имени** → дубли `<Item id>`; пример из практики: 134 добавленных имени и 5 дублей UUID,
  31 имя без объекта — сборка не принимается.
- `CheckModules` не видит ни дублей, ни orphan: модули компилируются.
- Загрузка в пустую базу проходит; ошибка проявляется в рантайме (обращение к предопределённому).
- Пустой `<PredefinedData/>` или отсутствие файла — не «нет предопределённых», а повод проверить,
  что файл вообще выгружен.
- `+N` наших имён — нормально, но каждое должно быть объяснено в отчёте сборки.
