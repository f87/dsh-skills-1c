# Склейка модулей BSL с учётом структуры и имён методов

Реализация: `config\update\blockmerge.js` (основной), `config\update\merge3v2.js` (3-сторонний текстовый merge),
контроль — `_work\scripts\checkmods.js` (скрипт конкретного проекта).

## Модель

Для каждого модуля три версии:

- `base` — новая поставка (например, 2.5.27.98);
- `old` — предыдущая поставка (2.5.22.186), то есть то, от чего мы отталкивались;
- `ours` — текущая конфигурация с доработками.

Переносим **наши** правки в `base`. Сравнение — по процедурам/функциям, а не по строкам файла.

## Правила вставки

1. **Наша процедура = `old`** (мы её не меняли) → берём `base` целиком.
2. **Правки внутри процедуры**:
   - блоки нашей области (`#Область …`, имя — в `markers.json`) — из `ours`, в конец соответствующей процедуры (приоритет выше `{УАТ}`);
   - блоки `{УАТ}` — если в `ours` отличаются от `old`, берём наш вариант; иначе — из `base`;
   - согласованные участки не трогаем.
3. **Новые процедуры/функции** (есть в `ours`, нет в `base`) — в конец модуля, с сохранением порядка.
4. **Полная замена процедуры** — только если совпала сигнатура и правки несовместимы; список таких процедур
   задаётся явно (`_work\lists\replace_procs.json`, в проекте 4 шт.), замена помечается маркером.
5. **Зашифрованные модули** (`Ext\Module.bin`, `слк*`) не сливаются — берутся из поставки.

## Запуск

```powershell
node config\update\blockmerge.js <base> <old> <ours> <out> [replace_procs.json] [markers.json]

`markers.json`: `{ "blockStart": "{НашБлок}", "blockEnd": "{/НашБлок}", "region": "НашаОбласть" }` —
маркеры блоков задаются файлом, значения по умолчанию условные.
```

Что делает текущая версия (`blockmerge.js`):

- заменяемые процедуры берутся из `ours` **целиком** и оборачиваются маркерами, если их ещё нет
  (маркеры вокруг всей процедуры, а не сигнатуры);
- из тела заменяемой процедуры убирается закрывающий маркер, попавший сразу после сигнатуры;
- модуль без нашей процедуры в поставке — процедура дописывается в конец с маркером и пометкой;
- BOM сохраняется.

После блочного слияния запускайте `carryprocs.js` — он переносит процедуры, добавленные без разметки
(`node config\update\carryprocs.js <resultFile> <currentFile> [report] [region]`), до неподвижной точки.

Статусы блоков в отчёте: `ctx` (вставка в контекст), `eop` (в конец процедуры), `repl` (замена целиком),
`manual` (требует глазами).

## Контроль

```powershell
node _work\scripts\checkmods.js <result> <current> <base> <report.json>
```

- `missing` — наши процедуры/функции, которых нет в результате: должно быть **0**;
- 1–2 остаточных «потери» часто артефакт чекера (новые процедуры в конце файла, маркеры сигнатур) —
  проверять вручную.

## Обязательные проверки после слияния

1. `CheckModules -ThinClient -Server` → `EXIT 0`, «Синтаксических ошибок не обнаружено!» (одиночный `-ThinClient` серверные модули не проверяет — `config/checkmodules.md`).
2. Поиск «осиротевших» ссылок на наши процедуры (`refscan`).
3. Выборочное сравнение сложных модулей с `ours` (маркеры `{УАТ}`/нашей области на месте).

## Грабли

- Не сливать по номерам строк: у поставщика меняется порядок процедур.
- Не вставлять `{УАТ}`-код в конец файла, если он относится к процедуре — будет «мертвый» код вне метода.
- PowerShell: не называйте функции `R`, `man`, `$args` (см. `1cv8/cli-gotchas.md`).
- После слияния не забывайте про маркеры: они нужны для будущих обновлений.
- **BOM.** До 21.10.2026 `blockmerge.js` терял BOM у модулей (читал с `\uFEFF`, писал без него):
  сравнение «наше дерево ↔ выгрузка 1С» давало ложные отличия (в проекте 34 `.bsl`). Исправлено:
  BOM сохраняется, если он был в `base`; CRLF сохранялся и раньше. R14 (`config/rules.md`) требует BOM.
