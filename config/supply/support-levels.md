# Уровни поддержки: расчёт 0/1 вместо копирования статусов

**Что это.** Правило и инструмент, которые расставляют уровни в `Ext\ParentConfigurations.bin` по факту
отличий нашего дерева от дерева поставки — вместо копирования статусов из базы заказчика.

**Когда применять.** При сборке конфигурации с доработками: после всех правок дерева (слияния, `fixconfig`,
переименования) и до `DumpCfg`. И при проверке уже собранной конфигурации — гейт 17 в
[`../update/acceptance.md`](../update/acceptance.md).

**Когда не применять.** К выгрузке живой базы заказчика: там уровни отражают историю правок, а не наше
решение (§1.1). Для точечных правок и принудительного снятия с поддержки остаются
[`../support-state.ps1`](../support-state.md) и `../support/set_levels.js`.

Формат файла, заголовок и токены — [`../support-state.md`](../support-state.md) §2. Здесь только правило
расстановки уровней.

## 1. Правило

В собранной конфигурации используем только уровни **0** и **1**. Уровень **2** — исключение, только по
прямому указанию владельца.

| уровень | значение | когда ставим |
|---|---|---|
| `0` | объект не редактируется = «на поддержке» | объект поставщика **побайтно совпадает** с поставкой: совпал файл `<Каталог>/<Имя>.xml` и все файлы каталога `<Каталог>/<Имя>/` |
| `1` | редактируется с сохранением поддержки | есть **любое** отличие от поставки — в самом объекте, в любой его форме, макете, справке, в любом реквизите или ТЧ |
| `2` | снят с поддержки | не используем; только если владелец явно решил, что объект больше не будет обновляться от поставщика |

Следствия, которые надо соблюдать буквально:

1. **Корень** получает `1`, если отличается **хотя бы один** его файл или любой вложенный элемент. Корень `0` —
   только когда все дочерние записи `0` и все файлы совпали.
2. **Табличная часть.** Изменённый или новый реквизит внутри ТЧ делает `1` саму ТЧ, а значит и весь документ.
3. **Реквизит, команда, макет, форма, справка** — любая правка тянет `1` на себя и на корень.
4. **Новые объекты и новые реквизиты** в `.bin` не попадают вообще (записи для них нет) — правило к ним
   не применяется.
5. **Режим (`mode`)** не трогаем: `0` остаётся `0`.

### 1.1. Почему нельзя копировать уровни из базы заказчика

Уровень `2` означает не «объект когда-то правили», а «мы больше никогда не хотим получать правки поставщика
по этому объекту»: такой объект выпадает из автоматического обновления. Если развернуть статус корня на
всё поддерево, из поставки выпадают реквизиты, формы и ТЧ, которые никто не трогал.

Пример (проект, сборка ЕРП 2.5.27.98 + модуль 2.5.22.1, 28.10.2026): прежний конвейер ставил `2` двумя
проходами — копировал статусы из базы заказчика и разворачивал их на поддерево. Итог в сданной
конфигурации: 8 230 записей уровня `2`, из них 5 478 — дети объектов, у которых в базе заказчика всё стояло
на `0`. Один документ с единственным добавленным реквизитом выглядел в Конфигураторе целиком снятым
с поддержки — потому что его корень был снят в базе заказчика ещё до нас.

## 2. Алгоритм расчёта

Вход: дерево поставки (`vendor`), наше дерево (`ours`), `.bin` поставки, `ConfigDumpInfo.xml`, два манифеста
хэшей (`node ../hash.js <tree> <out.json>`).

1. Читаем записи `.bin` и имена `uuid → Полное.Имя` из `ConfigDumpInfo.xml` (`<Metadata name="…" id="…">`).
2. Строим индекс «путь → ключи файлов» по манифестам хэшей обоих деревьев.
3. **Корень** `Каталог.Имя`: сравниваем набор ключей и SHA1 на префиксах `Каталог/Имя.xml` и `Каталог/Имя/`.
   Любое расхождение → корень `1`.
4. **Дочерняя запись:**
   - `Form` → каталог `…/Forms/<Имя>`;
   - `Template` → `…/Templates/<Имя>`;
   - `Help` → `…/Ext/Help`;
   - вложенная подсистема → отдельный файл `Subsystems/<A>/Subsystems/<B>.xml`;
   - остальные (реквизит, ТЧ, реквизит ТЧ, команда, ресурс, измерение) → блок XML с `uuid` записи внутри
     файла корня: сравнение нормализованного текста блока; для ТЧ — включая вложенные блоки реквизитов.
5. Уровень записи = `1`, если сравнение нашло отличия, иначе `0`.
6. Записываются только токены уровней; остальные токены не меняются (проверяется повторным разбором файла).

Две тонкости реализации, без которых расчёт врёт:

- **Сканирование блоков продолжается внутри корневого блока** (`re.lastIndex = m.index + m[0].length`):
  у корневого элемента тоже есть `uuid`, и его блок накрывает весь файл — иначе все дочерние блоки
  «проглатываются» и отчёт показывает 0 отличий.
- **Служебные файлы поддержки не сравниваются**: `ConfigDumpInfo.xml`, `Ext/ParentConfigurations.bin` и
  `Ext/ParentConfigurations/*`. Иначе корень `Configuration` получает `1` всегда — просто потому, что `.bin`
  поставки и нашего дерева не совпадают по определению.

## 3. Инструмент

```powershell
node config\supply\support-levels.js `
  --bin <tree>\Ext\ParentConfigurations.bin `
  --cdi <tree>\ConfigDumpInfo.xml `
  --vendor-root <vendorTree> --ours-root <tree> `
  --hashes-vendor <manifests>\vendor.json --hashes-ours <manifests>\ours.json `
  [--delivery <номер|имя>] [--only Catalog.Номенклатура] [--json <report>.json] [--out <new>.bin --write]
```

- без `--write` — только отчёт (dry-run), `.bin` не меняется;
- `--json` — сводка, список изменённых корней с примерами файлов и полный список изменений;
- `--only <ПолноеИмя>` — расчёт и печать по одному объекту (отладка правила);
- `--delivery` — какая поставка в `.bin` считается. При `count = 1` подставляется сама; при нескольких
  поставках параметр обязателен, записи остальных поставок прогон не трогает (каждая считается против
  своего дерева — §3.1). Для `.bin` с несколькими поставками удобнее `support-levels-multi.js`.

Коды возврата: `0` — расчёт (и запись) выполнены; `2` — не заданы обязательные параметры или нет `--out`
при `--write`; `3` — поставок несколько и не указана `--delivery`, либо имя поставки не найдено.

Отчёт (`--json`) содержит `summary` (поставка, `before`/`after` по уровням, `roots.changed/same`,
`levelChanges`, `blockChanges`), `changedRoots` и `changes`. `blockChanges > 0` означает, что отличия
найдены внутри блоков реквизитов/ТЧ, — это ожидаемо, если реквизиты правились на месте.

### 3.1. Несколько поставок

Для `.bin` с несколькими поставками — `support-levels-multi.js`: считает уровни **сразу для всех**
поставок, каждая против своего дерева и своего `ConfigDumpInfo.xml`.

```powershell
node config\supply\support-levels-multi.js `
  --bin <tree>\Ext\ParentConfigurations.bin `
  --ours-root <tree> --hashes-ours <h_ours>.json `
  --map <map>.json --json <report>.json `
  --out <tree>\Ext\ParentConfigurations.bin --write
```

`<map>.json` — массив в порядке поставок в `.bin`; пути разрешаются от текущего каталога:

```json
[{ "vendorRoot": "<vendorTree1>", "hashes": "<hashes1>.json", "cdi": "<vendorTree1>/ConfigDumpInfo.xml" },
 { "vendorRoot": "<vendorTree2>", "hashes": "<hashes2>.json", "cdi": "<vendorTree2>/ConfigDumpInfo.xml" }]
```

Правило для многопоставочного файла — то же, что §1, но применённое к каждой записи отдельно:

1. объект побайтно совпал с копией поставки `d` → `0` в записи поставки `d`, иначе `1`;
2. уровень главной поставки на записи второстепенных **не переносится** (см. ниже);
3. запись без путей в дереве своей поставки («висячая») → `1` и предупреждение;
4. запись без имени в `ConfigDumpInfo` не пересчитывается; `--write` при таких записях отменяется
   (код `4`), пока не задан `--allow-unresolved`;
5. корень поднимается до `1`, если хотя бы один дочерний объект `1`.

**Почему не переносим уровень главной поставки.** Уровень записи — утверждение о паритете с *этой*
поставкой: `0` значит «файл объекта не отличается от того, что поставил этот поставщик». Если у общего
объекта наш файл — версия главной поставки, для второстепенной это утверждение неверно, и `0` разрешает
1С при обновлении этой поставки заменить файл копией второстепенного поставщика (обычно более старой) без
вопроса. Поэтому у общего объекта может быть `0` в одной записи и `1` в другой — это его настоящее
состояние, а не рассинхронизация. Проверено 29.10.2026 на сборке ЕРП 2.5.27.98 + модуль 2.5.22.1:
общих по `uuid` записей 4 565, у 3 598 из них файл не совпал с копией модуля (`1`), у 967 совпал (`0`).

Тот же признак в живой базе (ЕРП 2.5.22.186 + модуль 2.5.21.1, 29.10.2026): из 4 552 общих по `uuid`
записей **ни одна** не имеет `0` в записи модуля — при `0`/`2` у ЕРП модуль даёт `2` (3 440) или `1` (1 112).
То есть 1С ведёт уровни по каждой поставке отдельно, и общий объект уровня главной не наследует.

Последовательные прогоны одноставочного `support-levels.js --delivery` дают тот же результат (второй
прогон записи первой поставки не меняет — §7.1), но требуют промежуточного файла и двух отчётов.

Числа прогона — §7.2.

## 4. Место в конвейере

```powershell
1) <сборка дерева: merge, fixconfig, переименования>          # уровни считаются ПОСЛЕ этого
2) node config\supply\support-levels.js ... --json <report>.json   # dry-run, сверить числа
3) node config\supply\support-levels.js ... --out <tree>\Ext\ParentConfigurations.bin --write
4) round-trip: загрузка дерева в чистую базу -> выгрузка -> сверка .bin (SHA1) и дерева
5) CheckModules -ThinClient -Server
6) DumpCfg -> <cf>
```

Если посчитать уровни раньше и потом править дерево — расчёт устареет: правка сдвинет SHA1 файлов,
и объект, ставший изменённым, останется с `0`.

При нескольких поставках шаги 2–3 заменяются одной командой `support-levels-multi.js` (§3.1): она же
даёт отчёт по каждой поставке — числа сверяются до `--write`.

## 5. Гейты

| # | гейт | норма |
|---|---|---|
| L1 | записей уровня `2` в `.bin` | 0 (или ровно согласованный список исключений) |
| L2 | `count` и `objects` | совпадают с исходным `.bin`, размер файла не изменился |
| L3 | `mode` записей | не менялся ни у одной записи |
| L4 | повторный расчёт независимым прогоном | расхождений 0 (идемпотентность) |
| L5 | round-trip `.bin` (Load → Dump) | SHA1 совпадает с записанным |
| L6 | выгрузка после round-trip | отличий от дерева нет, кроме `ConfigDumpInfo.xml` и `Ext\ParentConfigurations.bin` |
| L7 | корни уровня `1` | каждый имеет отличия против поставки; корней `0` с отличиями — 0 |
| L8 | корни `0` с дочерними `1` (многопоставочный `.bin`) | 0 |
| L9 | `bin_diff.js` до/после расчёта | состав записей и `mode` не менялись — только уровни |
| L10 | повторный расчёт на записанном многопоставочном `.bin` | изменений 0 (идемпотентность) |
| L11 | round-trip многопоставочного `.bin` (Load → Dump) | SHA1 совпал с записанным, обе копии `*.cf` на месте |
| L12 | записи без имени в `ConfigDumpInfo` (`unresolvedNames`) | 0; иначе их уровни не проверены и `--write` отменяется |

В конвейере это гейты 17–20 в [`../update/acceptance.md`](../update/acceptance.md).

## 6. Ограничения

- Сравнение файловое (SHA1), поэтому результат зависит от финальности дерева: BOM, порядок XML-элементов,
  локализованные имена (`РасширеннаяПодсказка`/`ExtendedTooltip`) дают `1` там, где содержательно отличий нет.
  Это дороже, но безопаснее: лучше лишний `1`, чем потерянная правка.
- Зашифрованные `Module.bin` (БСП и др.) сравниваются побайтно — работает; их правка даёт `1`.
- Если 1С при загрузке переупорядочит записи `.bin`, SHA1 изменится. В эксперименте порядок сохраняется
  байт-в-байт ([`deliveries.md`](deliveries.md) §3).
- Объекты, которых нет в поставке, записей в `.bin` не имеют — их «уровень» в Конфигураторе определяется
  только фактом отсутствия в поставке.
- Общий объект двух поставок может иметь разные уровни в разных записях (`0` в одной, `1` в другой) — это
  не рассинхронизация, а паритет с каждой поставкой по отдельности (§3.1).
- Инструмент меняет **только** уровни. Флаг конфигурации и поставок (`set_flags.js`), состав поставок
  (`build_two_deliveries_bin.js`) и порядок записей он не трогает.

## 7. Пример результата (проект)

Сборка ЕРП 2.5.27.98 + модуль 2.5.22.1, одна поставка в `.bin`, 159 954 записи, платформа 8.3.27.1859:

| | до | после |
|---|---|---|
| уровень 0 | 151 713 | **159 839** |
| уровень 1 | 11 | **115** |
| уровень 2 | 8 230 | **0** |

Корней проверено 22 330: изменено 110, совпало 22 220. Размер `.bin` не изменился (12 476 615 Б), `mode`
у всех записей остался `0`. Round-trip: загрузка дерева в чистую базу, выгрузка — `.bin` SHA1 совпал,
остальные 131 351 файл дерева побайтно те же (отличались только `ConfigDumpInfo.xml` и
`Ext\ParentConfigurations.bin`). Пример: документ с одним добавленным реквизитом — корень `2 → 1`,
все 178 дочерних записей `2 → 0`, сам новый реквизит записи не имеет.

### 7.1. Что проверено у самого инструмента (8.3.27.1859, 29.10.2026)

| Проверка | Результат |
|---|---|
| сухой прогон на паре деревьев (10 862 записи, одна поставка) | 106 изменённых корней, 1 595 совпавших; уровни `0`=10 671, `1`=191, `2`=0 |
| `--write` на тех же данных | размер `.bin` не изменился (847 478 Б), `count`/`objects`/`mode` те же, изменились только токены уровней (проверка внутри инструмента) |
| повторный прогон на записанном файле (идемпотентность, гейт L4) | `levelChanges` = 0 |
| `.bin` с двумя поставками, два прогона с `--delivery 0` и `--delivery 1` | каждый прогон изменил ровно 10 682 записи своей поставки; записи первой поставки после второго прогона не изменились (0 токенов), `count`=2, размер тот же |
| ошибки выбора поставки | при `count`=2 без `--delivery` — код 3 со списком поставок; `--delivery 7` — код 3; выбор по имени поставки работает |

### 7.2. Две поставки в одном `.bin` (8.3.27.1859, 29.10.2026)

Тот же набор объектов, что в §7, но `.bin` собран с двумя поставками: 13 324 077 Б, `count` 2, `flag=0`
у обеих, 170 816 записей (159 954 ЕРП + 10 862 модуль).

| поставка | записей | было `0`/`1`/`2` | стало `0`/`1`/`2` |
|---|---|---|---|
| УправлениеПредприятием 2.5.27.98 | 159 954 | 151 713 / 11 / 8 230 | 159 839 / 115 / 0 |
| МодульУправлениеАвтотранспортомДля1СERP 2.5.22.1 | 10 862 | 23 / 10 839 / 0 | 7 079 / 3 783 / 0 |

Разбор уровня `1` у модуля: 4 565 записей общих с ЕРП по `uuid` — у 967 файл совпал с копией модуля (`0`),
у 3 598 не совпал (`1`, наш файл — версия ЕРП); ещё 185 записей уровня `1` — собственные отличия модуля.

| Проверка прогона | Результат |
|---|---|
| `--write` | 13 324 077 Б, SHA1 `14176FF8…`; `count`/`objects`/`mode` те же (проверка внутри инструмента) |
| повторный прогон на записанном файле (L10) | `levelChanges` = 0 |
| `bin_diff.js` до/после (L9) | «только A 0 / только B 0» у обеих поставок, `mode` изменён 0, изменились только уровни (8 231 и 7 058) |
| корни `0` с дочерними `1` (L8) | 0 |
| записи без имени / без путей (L12) | 0 / 0 |

Round-trip именно этого файла (L11) не прогонялся — менялись только токены уровней, формат тот же.
В протоколе проекта прогонялся двухпоставочный `.bin` того же формата с другим набором уровней второй
поставки: `.bin` после загрузки и выгрузки совпал побайтно, обе копии `*.cf` на месте
([`deliveries.md`](deliveries.md) §4).
