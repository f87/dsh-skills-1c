# Работа с журналами в десятки гигабайт

Когда применять: файл не влезает в память, чтение идёт часами, нужно прервать
и продолжить, или посчитать несколько разрезов по одному и тому же файлу.

Замеры: журнал 21,5 ГБ / 198,3 млн записей, HDD, 32 ГБ RAM, Python 3.15 в один поток
(ноябрь 2026).

## Размеры, к которым нужно быть готовым

| Параметр | Значение |
|---|---|
| Средняя запись | ~115 байт (проверено: 114,6 на срезе 64 МиБ / 585 503 записи; 116,2 на другом срезе) |
| 1 ГБ файла | ~8–9 млн записей |
| Месяц работы средней базы | 5–25 ГБ |
| Таблица «запись = строка» в СУБД | в 2–2,5 раза больше файла со всеми индексами |

## Читать блоками, а не целиком

```python
with open(path, "rb") as f:
    carry, carry_base = b"", 0          # хвост прошлого блока и его абсолютное смещение
    while True:
        chunk = f.read(64 << 20)
        if not chunk:
            break
        data = carry + chunk
        base = carry_base               # абсолютное смещение data[0]
        ...
        cut = last_marker(data)         # -1, если маркеров нет
        if cut > 0:
            parse_block(data, base, cut)      # всё до последнего маркера
            carry, carry_base = data[cut:], base + cut
        else:
            carry, carry_base = data, base    # завершённых записей нет — копим
```

Перенос хвоста обязателен: без него теряется одна запись на каждый блок. На 21,5 ГБ
при блоках по 64 МиБ это около **343 записей** — ровно столько блоков. Именно эту величину
даёт расхождение «маркеров больше, чем строк», если считать маркеры без учёта переноса
(перенесённая запись видна в двух блоках). При аккуратном переносе потеря равна нулю —
это подтверждается независимым пересчётом с перекрытием, см. [`parsing.md`](parsing.md).

Первая итерация — единственная, где `data` может начинаться с `{`: так выглядит старт ровно
по `off` записи (смещение из базы). Этот случай нельзя путать с «маркеров нет»: разделитель
дописывается вручную, иначе первая запись выпадет (проверено 18.11.2026: `--from 61`
по `off` первой записи `Sample.lgp` даёт 3 из 3). Дальше `carry` всегда начинается с `\n`.

## Смещение записи — обязательное поле

Сохраняйте **абсолютное смещение `{`** каждой записи **вместе с именем файла** (`src`). Это даёт
мгновенный возврат к оригиналу: комментарий со стеком в таблицу не влезает, а по смещению
читается за миллисекунды ([`read_record.py`](read_record.py)). Без `src` смещение неоднозначно:
у журнала из нескольких `.lgp` одинаковые `off` встречаются в разных файлах.

```python
off = base + m.start() + 1     # m.start() указывает на '\n', запись начинается со следующего байта
```

Проверено: 20 случайных строк «CSV → off → read_record.py» дали совпадение по времени 20 из 20;
5 из 5 строк, взятых из SQLite по `src` + `off`, прочитаны тем же скриптом.

## Скорость: что во что упирается

| Режим | Скорость | Комментарий |
|---|---|---|
| Последовательное чтение HDD | 110–130 МБ/с | предел диска |
| Только регулярка (маркеры + шапка) | ~30 МиБ/с | замерено 31,7 МиБ/с |
| Полный разбор со сборкой строк | 17–19 МиБ/с | замерено 18,9 МиБ/с |
| Разбор + вставка в СУБД | 8–12 МиБ/с | узкое место — цикл и вставка |
| C#/Go вместо Python | в 3–5 раз быстрее | если нужен пересчёт за минуты |

Практический ориентир: 21,5 ГБ — около 35 минут на загрузку строк и 69 минут
на построение 13 индексов.

## Порядок операций при загрузке в базу

1. **Сначала данные, потом индексы.** Загрузка в таблицу без вторичных индексов и
   построение после — в разы быстрее.
2. **Одна транзакция на всю загрузку** или крупные пачки. Замер на SQLite: коммит на каждые
   50 тыс. строк — 15 тыс. строк/с; одна транзакция — 520 тыс. строк/с, разница в 35 раз.
   `load_sqlite.py` держит одну транзакцию и пачки по 50 тыс. строк.
3. **Сверка после каждой фазы**: независимый счётчик маркеров против числа строк.

## Возобновление после сбоя

- Точка возобновления — байтовое смещение последнего разобранного блока **или** `off`
  последней разобранной записи: `--from <off>` не теряет запись, с которой начали
  (парсер восстанавливает разделитель, см. [`parsing.md`](parsing.md)).
- Промежуточные результаты (счётчики, агрегаты) сохраняйте в отдельный файл **до** тяжёлой
  сборки итогов. Падение на этапе отчёта тогда стоит секунды, а не повторного чтения 21 ГБ.
- Если прервалось построение индексов, не перечитывайте журнал: `load_sqlite.py --db <файл>
  --only-indexes` достроит недостающие индексы в готовой базе (`CREATE INDEX IF NOT EXISTS`),
  данные и TSV не нужны.

## Параллельная обработка

Записи независимы, каждая начинается с `\n{` + 14 цифр + `,`, поэтому файл режется
на диапазоны и обрабатывается в несколько потоков с локальными счётчиками и слиянием в конце.

**В `parse_lgp.py` этого режима нет** — скрипт однопоточный. Приём описан для случая, когда
нужен пересчёт за минуты на своей обвязке (или на C#/Go).

Ограничения:

- границы диапазонов выравнивать по маркеру (первый `\n{14 цифр,` после начала диапазона);
- на HDD выигрыша почти нет — упор в диск; на NVMe ускорение линейное до числа ядер;
- 4 потока × 64 МиБ — нормально по памяти.

## Память

Читать блок целиком (64 МиБ) и держать список позиций маркеров — приемлемо:
на 64 МиБ это ~600 тыс. целых, порядка 20 МБ. Чего делать не стоит — копить **объекты
совпадений** (`list(finditer(...))`) на весь файл и складывать все записи в один список
перед вставкой: это десятки гигабайт.

## Место на диске

Файл журнала + таблица в СУБД (2–2,5×) + временные файлы сортировки индексов.
Для 21,5 ГБ журнала закладывайте 60–80 ГБ свободного места.

## Проверка

```bash
python parse_lgp.py --input <файл.lgp> --limit 67108864 --check   # счётчики равны, «не разобрано» 0
python parse_lgp.py --input <файл.lgp> --from <off> --limit 10000000
python read_record.py --input <файл.lgp> --offset <off>
```

- «учтено» и «контроль» совпадают, «не разобрано» = 0 — перенос хвоста работает;
- `--from` по `off` записи не теряет эту запись (проверено: 3 из 3 на `Sample.lgp`);
- 20 случайных строк выгрузки, прочитанных `read_record.py` по `off`, совпадают по дате
  (проверено 20 из 20); при наличии `src` — 5 из 5 по `src` + `off`.

## Чего не делать

- `readlines()` и построчное чтение — записи многострочные;
- загружать файл в память целиком «ради удобства»;
- строить индексы в той же транзакции, что и загрузку;
- запускать загрузку без настройки журналирования СУБД — настройки дают кратное ускорение.
