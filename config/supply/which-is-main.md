# Какая поставка главная и в каком порядке собирать

Универсально для любой конфигурации 8.3 с несколькими поставками. Проверено 8.3.27.1859, 28.10.2026.

Порядок поставок в `Ext\ParentConfigurations.bin` 1С **не проверяет**: файл с обратным порядком
загрузился без единого сообщения ([`deliveries.md`](deliveries.md) §4). Значит порядок — наша
конвенция, и задавать его нужно по смыслу, иначе получается конфигурация, где «своей» поставкой
объявлен модуль-дополнение (так исторически и было в базе проекта проверки).

**Правило: главная поставка — первая.**

---

## 1. Признак 1 (основной): совпадение «имя, версия» с `Configuration.xml`

Пара `(Name, Version)` — то, что 1С показывает в «О программе» и что задаёт идентичность продукта.
Главная — поставка, у которой `name` и `version` **совпадают** с `Configuration.xml` собираемой
конфигурации; `vendor` — контрольное поле.

```xml
<Configuration uuid="…"><Properties><Name>…</Name><Version>…</Version><Vendor>…</Vendor>…
```

Сверять с полями поставки, которые печатает `support-state.ps1 -Tree <tree>` или
`config\supply\bin_summary.js`.

Пример (проект проверки):

| Источник | Name | Version | Vendor |
|---|---|---|---|
| `Configuration.xml` сборки | УправлениеПредприятием | 2.5.27.98 | Фирма «1С» |
| поставка продукта | УправлениеПредприятием | 2.5.27.98 | Фирма «1С» | ← **главная** |
| поставка модуля | МодульУправлениеАвтотранспортомДля1СERP | 2.5.21.1 | Фирма «1С-Рарус» | дополнение |

## 2. Признак 2 (страховка): вендор

Если совпадения по имени/версии нет (конфигурация переименована, поставка переупакована), главной
считается поставка **вендора продукта**, дополнением — поставка стороннего отраслевого вендора:

- продукт: вендор платформенной конфигурации («Фирма "1С"» и родственные);
- дополнение: отраслевой вендор, например «Фирма "1С-Рарус"».

Подкрепляющие признаки того же вывода: имя дополнения обычно само говорит, что это модуль
(`Модуль…Для1С…`), его `.cf` на порядки меньше, а объекты дополнения ссылаются на объекты продукта,
но не наоборот.

## 3. Что НЕ является признаком

| Не признак | Почему |
|---|---|
| порядок поставок в существующем `.bin` | мог сложиться исторически и быть неверным |
| заголовок «О программе» | берётся из `Configuration.xml`, а не из поставок; в базе проекта там стоял продукт, хотя «своей» поставкой был модуль |
| уровни поддержки `0/1/2` | это история правок, а не главенство |
| `parentGuid == supportGuid` | это определение «своей» поставки в файле, но не критерий: файл можно собрать с любым «своим», 1С примет молча |
| число записей / размер `.cf` | следствие, а не критерий |

## 4. Порядок сборки

1. Главная поставка — первая. Её `parentGuid` = заголовочный `supportGuid` (для первой поставки
   отдельного токена нет — [`support-state.md`](../support-state.md) §2.1).
2. Дополнение — второй поставкой.
3. `flag=0` **обеим**, иначе 1С удалит копию `*.cf` дополнения ([`deliveries.md`](deliveries.md) §2.2).
4. Копии `*.cf` обеих поставок — в `Ext\ParentConfigurations\`, байтовые копии вендорских файлов.

Сборка — [`build-and-check.md`](build-and-check.md), инструмент — `build_two_deliveries_bin.js`
(--order main, --header main). Менять порядок можно, **состав** — нет: при обновлении число поставок
сохраняется ([../update/deliveries-invariance.md](../update/deliveries-invariance.md)).
